## obfmesh-onwatch 1.0.0 — недоступный сайт уезжает в луч сам, и ничто при этом не перезапускается

Третий пакет проекта, рядом с `obfmesh` и `obfmesh-balance`. Требование поставлено дословно:
«ронять нельзя интернет на постоянной основе, необходимо придумать реактивную альтернативу». Всё
устройство пакета выведено из него: заворачивание цели — это одна транзакция `nft add element` в
живое множество. Ни dnsmasq, ни sing-box, ни Forkop, ни firewall не перезапускаются, открытые
соединения не рвутся, `uci commit` при заворачивании не делается ни разу. Человек видит результат
после F5 — заворот действует на новые соединения.

Версионируется пакет отдельно, мест два, как у балансировщика (PACKAGING.md, 4.1):
`openwrt/obfmesh-onwatch/Makefile` (`PKG_VERSION`) и
`openwrt/obfmesh-onwatch/files/usr/lib/obfmesh-onwatch/lib.sh` (`OWN_VERSION`). `obfmesh` 1.4.0 и
`obfmesh-balance` 1.2.0 не менялись. Нижняя граница `obfmesh` для onwatch — **1.4.0**: состав лучей
берётся целиком из `obfmesh status --json` (`index`, `iface`, `source_address`, `table`, `link_up`,
`handshake_age`), а до 1.3.0 его `apply` вдобавок сносил чужие правила в своих таблицах `51820+i` —
правила `30000+i` не пережили бы первого же `apply`. В `DEPENDS` это не выражается, поэтому границу
проверяют `postinst` (предупреждением) и `install-nosdk.sh` (отказом).

**Пакет на роутер не выкачен.** Разведка и все замеры ниже сняты на живом роутере, код проверен
тестами на рабочей машине. Порядок выката — DEPLOY.md, шаг 11; он требует отдельного разрешения,
как и любая установка.

### Детектор по SYN_SENT ловил бы не тот класс блокировок

Первая гипотеза была очевидной и неверной: считать заблокированной цель, чьё соединение висит в
`SYN_SENT`. Проверка на живом роутере: из **16 доменов заблокированы 6, и у всех шести
TCP-рукопожатие проходит успешно** — в conntrack они `ESTABLISHED`, а RST прилетает на ClientHello
(`curl` rc=35). Детектор по `SYN_SENT` прошёл бы мимо всех шести.

Настоящая чёрная дыра нашлась ровно одна — `rutor.info`. Поэтому в пакете два сенсора и два разных
порога: `rst_threshold` (по умолчанию 2) на инжектированный RST и `syn_threshold` (3) на молчание.
Второй порог выше намеренно: молчащий сервер — это ещё и обычная авария на той стороне, и
заворачивать её в луч незачем.

### Отпечаток инжектированного RST — `tcp window 32`

Признак, по которому подделка отличается от честного RST закрытого порта: **окно 32**. Снят с
**45 живых RST на этом роутере, ложных срабатываний ноль**. Отсюда правило цепочки `sense`:

```
tcp sport { 80, 443 } tcp flags & (fin|syn|rst|ack) == rst tcp window 32 ip saddr != @never4
	update @rst_hits { ip saddr . tcp sport }
```

Сенсоры живут в ядре целиком: `@rst_hits` и `@syn_watch` — динамические множества с `timeout` и
`counter`, ни одного пакета в пользовательское пространство не поднимается. Демон раз в такт читает
счётчики и сравнивает их с порогами.

Способность ядра принять это выражение проверяется пробой `nft -c -f -`, а не наличием пакета
`kmod-*`: на этой прошивке ядро 6.1.141 из BSP FriendlyElec, а `kmod-*` в её feed собраны под
6.12.94 — ровно так в августе не встал `kmod-amneziawg`. Тот же приём, что у балансировщика.

### Захват DNS на петле бесплатен именно потому, что dnsmasq собран с `cache-size=0`

Имена целей брать больше неоткуда: детектор ловит адреса, а человеку нужен домен, и при
`require_domain = 1` без имени не заворачивается ничего. Источник один — пассивный захват ответов
DNS на `lo` между dnsmasq и sing-box.

Работает это на одном свойстве прошивки: **dnsmasq собран с `cache-size=0` и единственным апстримом
`127.0.0.42`, поэтому КАЖДЫЙ внешний запрос клиента физически летит по петле открытым текстом**.
Кеша нет — значит нет и невидимых попаданий в него.

Цена замерена, а не прикинута: `lo` несёт **7 пакетов/с**, `br-lan` в простое — 976, `eth0` на
полосе 430 Мбит/с — около 72000. Одно срабатывание AF_PACKET+BPF на этом A55 стоит ~2.2 мкс, то
есть захват на петле — **0.003 % ядра**, а на `br-lan` или `eth0` он стоил бы **до 16 % одного
ядра**. Потолок 430 Мбит/с на этом роутере задан именно процессором, поэтому захват где-либо, кроме
`lo`, запрещён. Сам `tcpdump` в userspace не стоит ничего: **0 jiffies за 30 секунд**, вся цена в
ядре. Форки: ~0.2 в секунду в простое.

Задержка у такого источника **отрицательная**: имя известно раньше, чем клиент отправит SYN.

Дедупликация обязательна: петля отдаёт один и тот же пакет точке захвата дважды, а в захвате
встречаются и тройки одинаковых строк. Ключ — txid ответа плюс исходное имя: дубликат приходит тем
же пакетом, а повторный запрос того же имени dnsmasq отправляет с новым txid и заглушён не будет.

### Ключи `tcpdump`: `-v` обязателен, `-q` ломает, `-vv` врёт

Строка команды проверена на живом роутере целиком, и каждый ключ в ней держится на наблюдении:

```sh
tcpdump -i lo -nn -l -v -s 512 --immediate-mode 'udp src port 53 and src host 127.0.0.42'
```

- **`-v` обязателен.** Имя владельца записи `tcpdump` печатает только при `vflag`. Без него строка
  выглядит как `1/0/1 A 140.82.121.4`, и восстановить, какое имя спрашивали, физически нечем.
- **`-q` ломает разбор целиком**: строка превращается в `UDP, length 283`, записей в ней нет вовсе.
- **`-vv` даёт враньё.** Он печатает и секцию additional, а glue-записи оттуда привязались бы к
  спрошенному имени — в карту имён попал бы адрес чужого сервера имён под именем сайта.
- `-l` — без него вывод в канал буферизуется по 4 КиБ, и имя доезжает через сотни запросов после
  того, как клиент уже открыл соединение.
- `-nn` — чтобы порт печатался числом (разбор опирается на `.53 > `) и чтобы `tcpdump` не ходил в
  DNS сам.
- `-s 512` — хватает на ответ с цепочкой CNAME; обрезанный хвост помечается `[|domain]`, и разбор
  такую запись переживает.

### Прежде чем завернуть — проба, и исход читается по коду возврата curl, а не по http_code

Заворачивается цель **только когда напрямую плохо, а через луч хорошо**. Проба идёт дважды: прямо и
через луч, с настоящим адресом через `--resolve` (имя, уже ушедшее в обход, резолвится в FakeIP
`198.18.x.x`, который в туннель не маршрутизируется, — проба по нему проверила бы несуществующий
маршрут). Не помогло и через луч — цель уходит в карантин: сайт лежит целиком, а не блокируется, и
долбить его пробой каждые несколько секунд незачем.

Исход определяется **кодом возврата `curl`**, и это не вкусовщина: `http_code` `000` отдают и обрыв
на ClientHello, и негодный сертификат, то есть и блокировка, и не блокировка.

| rc | Что это | Решение |
|---|---|---|
| 35 | обрыв на рукопожатии TLS — инжектированный RST на ClientHello, главный класс здесь | похоже на блокировку |
| 28 | связи нет вовсе | похоже на блокировку |
| 56 | обрыв уже на данных (тот же приём на 80-м порту, где рукопожатия TLS нет) | похоже на блокировку |
| 60 | сертификат не принят | чужая беда, луч её не чинит — карантин |
| 0 с кодом 403 или 451 | так отвечают совершенно РАБОЧИЕ сайты (`grok.com`, `chatgpt.com`, `notion.so`) | не заворачиваем |

### Цена такта: 222 процесса каждые пять секунд стали 15

Считалось обёртками перед `PATH` (запуски программ) и по коду (подоболочки `$( )` и стадии
конвейеров — `exec` они не делают и обёрткам не видны). На роутере процесс стоит и там и там.

| Состояние такта | Процессов |
|---|---|
| покой: улик нет | **13** |
| улика есть, но ниже порога | **15** |
| было раньше в том же состоянии | **222** |

При такте в пять секунд это **180 процессов в минуту вместо 2664**, и держалась дорогая цифра не
мгновение: улика живёт десять минут, и все десять минут такт с ней стоил своих 222 процесса каждые
пять секунд. Дорогое чинилось отдельно и в двух местах. Первое: обслуживание (лучи, правила, ruleset, снимки множеств, запись состояния) шло по
признаку «что-то завёрнуто» — то есть каждый такт ровно в том состоянии, ради которого пакет и
написан: цель завёрнута, улика истекла, решать нечего. Теперь оно идёт по расписанию: раз в 30
секунд в покое и раз в 15, когда завёрнуто хоть что-то. Второе: экранирование JSON конвейером
`printf | sed | tr` на КАЖДОЕ поле — 88 запусков из 144 на записи `state.json`; теперь то же самое
делает сам шелл подстановкой параметров и не стоит ни одного процесса.

### Ложная тревога: 50 соединений на WAN-адрес роутера, которых нет

Разведка началась с числа, которого не было. Скрипт считал в `/proc/net/nf_conntrack` соединения к
WAN-адресу роутера и находил **50 штук**. В записи conntrack адреса стоят **дважды**: прямое
направление и обратное, уже после SNAT, — и жадный разбор брал вторую тройку, где в `dst=` как раз
и стоит WAN-адрес самого роутера. То есть считались все обычные транслируемые соединения дома.
**Настоящее число — ноль.**

Записано затем, чтобы не выяснять это второй раз: считать по conntrack можно только с привязкой к
направлению, а не грепом по адресу в строке.

### Устройство: своё и только своё

Инвариант тот же, что у соседей: ни один компонент не пишет в чужое.

- своя таблица `nft inet obfmesh_onwatch`;
- своя полоса `ip rule`: `30000+i` — правила лучей, `30500+i` — их персональные страховки,
  `30511` — общая страховка на любой номер луча;
- свои биты метки: база `0x02000000`, номер луча в младшем байте, селектор
  `fwmark 0x2000001/0x20000ff`. Бит tproxy Forkop `0x04000000`, байт `0x0000FF00`
  (номер луча у obfmesh-balance) и младший байт базы запрещены, и конфигурация проверяет это сама;
- два процесса procd: `sniff` (захват) и `daemon` (решатель), `START=97`, `STOP=8` — строго после
  соседей на старте и строго раньше них на остановке.

**Страховка обязательна, и это проверено, а не выведено.** Метка без своего правила — не отказ, а
утечка: `ip route get 1.1.1.1 mark 0x02000001` без правила отвечает `via 37.9.41.254 dev eth0`, то
есть пакет уходит к провайдеру открытым текстом — ровно к тому, от кого сайт и заворачивали. Со
страховкой он отбрасывается. Отсюда и порядок: правила и страховки ставятся ДО таблицы, снимаются
ПОСЛЕ неё.

### Ставится выключенным и в сухом ходу

Два выключателя, и снимаются они по очереди. Пока `enabled = 0` — нет ни таблицы, ни единого
`ip rule`. Пока `dry_run = 1` — детектор считает, объясняет и пишет журнал решений, но НИ ОДНУ цель
не заворачивает. Сухой ход — рабочий режим первых суток, а не отладка: цена ошибки в обратную
сторону — ложно опознанная цель, уехавшая в луч автоматически и молча, и для человека это выглядит
не как поломка, а как «сайт стал медленнее» (завёрнутый трафик идёт мимо flowtable — в `ft` лежат
`br-lan`, `docker0` и `eth0`, но не `owg`).

### Чего пакет не может — по пунктам, чтобы не искали

1. **Различить устройства.** За двойным NAT весь дом — один адрес `192.168.2.151`, а на `lo`
   теряется и он: источник всегда `127.0.0.1`.
2. **Узнать домен при заходе по голому IP без DNS** — торренты, игры, вшитые адреса.
3. **Увидеть запросы по DoH и DoT.** Они идут по 443 и 853 и неотличимы от обычного трафика. Это
   граница метода, а не сбой: имени у такой цели не будет НИКОГДА. Мера этой слепоты — доля
   кандидатов, отвергнутых из-за отсутствия имени; она пишется в `last_reason` файла `state.json` и
   строкой в лог. Лечится только `obfmesh-onwatch pin <имя>`.
4. **Отличить блокировку от 403/451 полностью рабочего сайта** — см. таблицу исходов пробы выше.
5. **Отличить блокировку по SNI от блокировки по IP.** Выражения SNI в nftables 1.1.6 не
   существует.
6. **Порвать уже открытые соединения.** Утилиты `conntrack` в прошивке нет. Заворот действует на
   новые; человек видит результат после F5.
7. **Поймать деградацию** — медленно, рвётся на середине. Это не отказ, сигнала нет.
8. **QUIC и IPv6.** Детектора для UDP/443 нет, глобального IPv6 на роутере нет вовсе. Оговорка:
   когда пара адрес.порт уже завёрнута, цепочка `pick` уводит в луч и UDP к ней — но опознать цель
   по QUIC она не может.
9. **Заменить Forkop.** Пакет не умеет доменных правил sing-box и не выдаёт FakeIP. Это временная
   мера до переноса домена в секцию `on_test` — единственная операция во всей фиче, которая требует
   `uci commit` и рвёт связь всему дому (INSTALL.md, 3.9.6).

## 1.4.0 и obfmesh-balance 1.2.0 — счётчик вместо жребия, ровные веса и RPS мимо ядер обфускаторов

Сессия на живом роутере 24.08.2026: искали, куда девается полоса при работающей балансировке. Нашли
три разные вещи — регулятор, который давил не на ту педаль, раскладку, которая делила в среднем, и
маску RPS, съедавшую пятую часть полосы. Всё проверено на боевом NanoPi R3S, замеры сняты с
клиента Win10.

Версии подняты: `obfmesh` `1.3.0` → **1.4.0** во всех четырёх местах из PACKAGING.md, 4.1,
`obfmesh-balance` `1.1.0` → **1.2.0** в обоих своих. У обоих MINOR, а не PATCH, и по одной причине:
поведение по умолчанию изменилось там, где оно наблюдаемо снаружи. У `obfmesh` пустой
`tune_rps_cpus` теперь значит «все ядра минус занятые обфускаторами», а не «все ядра», и по номеру
на роутере видно, какая из двух масок туда легла. У балансировщика цель регулятора стала
константой, раскладка перешла на `numgen inc` с чередующейся картой, добавилась опция `adapt`, —
и `obfmesh-balance version` отвечает на вопрос, гуляющие веса здесь дефект или прежняя норма.
Ломающего в обоих нет: формат бандла не тронут, uci-конфиги совместимы снизу вверх, ни одна опция
не удалена.

Нижняя граница `obfmesh` для балансировщика осталась **1.3.0** и вместе с версией не поднималась:
она держится на свойстве «apply не сносит чужие правила в своих таблицах», которое появилось именно
в 1.3.0, а не на номере последнего релиза. Балансировщику 1.2.0 от `obfmesh` 1.4.0 ничего нового не
нужно — маска RPS стоит полосы, а не работоспособности, — и поднять границу значило бы заставить
`install-nosdk.sh` отказывать там, где пара работает.

### Регулятор: цель больше не «равный прирост байт», а ровные доли

Прежний регулятор считал долю луча в суммарном приросте за такт и двигал вес в обратную сторону.
На этом роутере такая цель работала против задачи, и причин ровно четыре:

- **Прирост — мера обслуженного спроса, а не ёмкости луча.** Оба луча идут на один сервер через
  обфускаторы на соседних ядрах одного процессора. Узкое место — процессор роутера. Луч, тянущий
  больше, не перегружен, а продуктивен.
- **Педаль не соединена с колесом.** Вес управляет ТОЛЬКО новыми соединениями. Уже открытые
  прибиты к лучу через `ct mark` и переехать не могут: сервер отбросит пакет с чужим адресом
  источника. Снижение веса не отнимает у них ни байта — прирост на луче не падает, и регулятор
  давит всё сильнее. Снято с роутера: `owg1` вес 90 прирост 1.5K, `owg2` вес 10 прирост 5.2K, и
  формула требовала опустить `owg2` до `min_share`, то есть погасить ровно тот луч, который стоило
  нагрузить.
- **Чистый интегратор на объекте с запаздыванием даёт предельный цикл.** В логе он и был:
  90/10 → 75/25 → 60/40 → 75/25 → 90/10 каждые пять-шесть секунд, шаг всё время упирался в
  `max_step`.
- **Целочисленное усечение долей давало храповик.** Сумма долей выходила меньше ста, сумма целей —
  больше, остаток каждый такт снимался с базового луча мимо `max_step`. При практически равной
  нагрузке (1001 против 1000 байт) веса уезжали 49/51, 48/52, 47/53 — по пункту за такт, двенадцать
  пунктов в минуту, до самого `min_share`. То есть `auto` не удерживал даже ровную раскладку.

Теперь неподвижная точка **задана, а не вычислена**: при лучах равной ёмкости оптимальная доля
известна заранее и равна `1/N`. `mode = auto` ведёт веса к ровным долям шагами не больше
`max_step`, а прирост байт ушёл туда, где ему и место, — в диагностику (`DELTA` в `status`,
`state.json`). Осцилляции нет по построению: цель — константа, а не результат прошлого такта.

Проверено на роутере: под нагрузкой веса стояли 50/50 сорок секунд подряд, ни одной смены. Прежний
регулятор на том же месте осциллировал с периодом в четыре такта.

Адаптация не выброшена, а вынесена в опцию `adapt` (`off` по умолчанию, `conns`), и меряет она не
байты, а **число активных соединений** на луче — ту величину, которой регулятор управляет: поставили
соединение, счётчик вырос в тот же момент, без запаздывания. Счёт снимается одним проходом `awk` по
`/proc/net/nf_conntrack` по метке соединения. Цена замерена: 20 мс на такт при 141 записи (из них
8.5 мс — сам форк), дальше около 0.08 мс на запись; под торрентами это сотни миллисекунд на
процессоре, который и так узкое место. Поэтому по умолчанию выключено.

### Раскладка соединений: `numgen inc` по точечной карте вместо `numgen random`

Было: `numgen random mod 100` и карта из двух сплошных диапазонов. Стало: `numgen inc mod 100`,
карта из ста точечных позиций, без `flags interval`, а позиции распределены между лучами методом
наибольших остатков — **вперемешку**. При 50/50 это строгое чередование, при 70/30 в любом окне из
десяти позиций ровно три достаются второму лучу.

**Счётчик и чередующаяся карта — одно решение, а не два, и порознь они хуже жребия.** `inc` со
сплошными диапазонами — худшее из возможного: восемь подряд открытых соединений получают восемь
подряд идущих позиций и попадают в один диапазон целиком, то есть все восемь в один луч. Пятьдесят
подряд на один луч — ровно то, что даёт `inc` по диапазонам `0-49` и `50-99`. Чередующаяся карта
со жребием — это просто жребий: раз позиция берётся наугад, её место в карте не значит ничего.
Вместе они дают долю, соблюдённую на любом отрезке, а не в среднем.

**Честный вывод по замерам: после настройки RPS разница между `inc` и `random` — в пределах шума.**
Восемь потоков с клиента дали 318 и 364 Мбит/с на жребии до тюнинга, 377 и 382 после тюнинга и
374, 421, 386 на счётчике. Главным источником разброса оказался не клумпинг соединений, а маска
RPS. `inc` оставлен по трём причинам, и «он быстрее» среди них нет: он не хуже, точечная карта
дешевле в ядре (хеш вместо дерева интервалов, поиск за постоянное время), и на тихом роутере он
делит ровно, а не в среднем.

**Предел, который нельзя замалчивать: счётчик один на роутер.** Фазу сдвигает любое постороннее
соединение, прошедшее через цепочку. Наблюдалось прямо в этой сессии: восемь потоков замера плюс
два фоновых соединения легли **4/6**, а не 5/5. Ровными гарантированы доли позиций в карте, а не
конкретный набор соединений, который открыл человек.

Цена сборки карты замерена на роутере (Cortex-A55 1.5 ГГц, busybox ash): сто позиций — 14 мс на
двух лучах, 28 мс на трёх, 60 мс на десяти, против 2.2 мс у прежних сплошных диапазонов. Платится
она не каждый такт, а только на смене весов или состава лучей.

### Настройка роутера: RPS уходит с ядер, занятых обфускаторами

Самая дорогая находка сессии. Прибить обфускаторы к `cpu2-3` и оставить RPS на всех четырёх ядрах —
это половина изоляции: приём всё равно затаскивают на те же ядра, где крутится обфускатор.

Один и тот же луч, переставленный по ядрам (8 потоков по 100 МБ, замер с клиента):

| Ядро обфускатора | Скорость | Накоплено NET_RX softirq на этом ядре |
|---|---|---|
| cpu0 | 254 Мбит/с | 88 млн |
| cpu1 | 250 Мбит/с | 140 млн |
| cpu2 | 248 Мбит/с | 123 млн |
| cpu3 | **342 Мбит/с** | 38 млн |

Асимметрия шла **за ядром, а не за лучом**: обфускаторы меняли местами, и быстрым каждый раз
становился тот, кто уезжал на `cpu3`. Объяснение единственное — `cpu3` был тем ядром, куда RPS
почти не заносил приём. Частоты у всех четырёх одинаковые (1800 МГц, governor `performance`),
аппаратные прерывания `eth0`/`eth1` и так сидят на `cpu0-1` (`smp_affinity=3`), так что дело не в
железе и не в частотах.

Что сделано: при пустом `tune_rps_cpus` маска считается как «все ядра машины МИНУС те, на которые
привязка обфускаторов реально легла» — на R3S с двумя лучами это `3`, приём остаётся на `cpu0-1`.
Раньше по умолчанию бралась маска всех ядер (`f`). Заданное руками значение по-прежнему сильнее
вычисленного; если свободного ядра не осталось вовсе, шаг не выключается молча — в лог уходит
строка с причиной.

Замеры с клиента Win10 (8 потоков по 100 МБ, cachefly, домен заведён в секцию `speedtest`):

| Что мерили | Результат |
|---|---|
| исходное состояние: сервис жёстко прибит к лучу | ~270 Мбит/с |
| балансировка 50/50 до тюнинга | 318 и 364 Мбит/с (разброс между прогонами) |
| после `tune_rps_cpus=3` | 377, 382 Мбит/с |
| **итог: тюнинг плюс балансировка** | **411 Мбит/с** |
| то же на `numgen inc` | 374, 421, 386 Мбит/с |

Потолок 411 Мбит/с задан процессором роутера целиком: под нагрузкой idle 2 %, sirq 53 %, sys 44 %.

Про устойчивость маски: `rps_cpus` сбрасывают редкие сетевые события (перерегистрация устройства,
чужой `sysctl -p`), но постоянного стороннего писателя нет — значение держится сколько угодно, пока
его не сбили. Чинит `obfmesh` на своём тике, поэтому окно расхождения — до шести минут.

### Замер с роутера занижает вдвое, и это не поправка, а запрет

Снято в одну сессию: **157 Мбит/с с роутера против 348 с клиента**. Причина не в схеме, а в
процессоре — `curl` на роутере конкурирует за такты с sing-box и обфускаторами, которые тот же
трафик и обслуживают. Вывод в документации везде один: мерить только с клиента, цифру с роутера в

## obfmesh-balance 1.1.0 — пилот на живой сети и защита от недоведённого перевода секций

Первый выкат балансировщика на боевой роутер: obfmesh 1.3.0 и obfmesh-balance 1.0.0, живая домашняя
сеть, работающий Forkop, 23.08.2026. Раскладка заработала, и на ней же вскрылся дефект, которого не
видно ни на стенде, ни глазами оператора. Ради него версия и поднята.

Версия балансировщика поднята в обоих местах из PACKAGING.md, 4.1 — `1.0.0` → `1.1.0`. MINOR, а не
PATCH: `obfmesh-balance on` научился отказывать, и по номеру версии на роутере видно, есть в пакете
эта защита или нет. `obfmesh` не менялся и остаётся 1.3.0.

### Что подтвердилось на живой сети

Это первая проверка боевым трафиком: до пилота ruleset и транзакции были проверены только через
`nft -c -f` (запись 1.3.0, «Чего нет и что не проверено», п. 1).

- **Соединения расходятся по лучам.** Двадцать запросов через секцию `speedtest` — ту самую,
  которая переведена на `inet4_bind_address` базового луча, — ушли **18 через `owg1` и 2 через
  `owg2`**. Одна секция, один сервис, разные лучи: то, чего раскладка по сервисам (INSTALL.md, 3.7)
  дать не может в принципе.
- **SNAT переброшенного соединения работает.** В записи conntrack прямое направление —
  `src=10.77.1.2 dst=<цель>`, обратное — `dst=10.77.2.2`: ответа ждут на адресе второго луча, то
  есть подмена источника состоялась. Без неё пакет умирал бы на сервере — у пира в AllowedIPs ровно
  `10.77.{i}.2/32`.
- **Регулятор считает веса сам.** Демон увидел прирост `owg2` **21.7M** против `owg1` **2.3M** и
  переписал раскладку с **50/50 на 90/10**: луч, тянущий больше честной доли, получает вес пониже, и
  новые соединения идут в него реже.
  **Записано как достижение, оказалось дефектом** — разобрано 24.08.2026 (запись выше): вес
  управляет только новыми соединениями, открытые прибиты к лучу через `ct mark`, и регулятор гасил
  как раз тот луч, который стоило нагрузить. Выравнивание прироста байт из решения убрано,
  `mode = auto` ведёт ровные доли.
- **Страховка встала.** `blackhole` второго луча на `pref 31502` — на месте. Как выяснилось дальше,
  она же и отработала.

### Что вскрылось: под фильтр по адресу базового луча попадают и секции с его `bind_interface`

Цепочка `out` отбирает пакеты по двум признакам сразу: `meta mark 0x08000000` и
`ip saddr 10.77.1.2`. Второй признак задумывался как «секция переведена на `inet4_bind_address`
базового луча». На деле тот же адрес источника получает **любая** секция, чей `bind_interface`
указывает на интерфейс базового луча: `10.77.1.2` — единственный адрес на `owg1`, ядро выберет его
при `connect()` само. На боевом роутере таких секций было три: `apple`, `wgobf`, `kinopub`.

Отличие от переведённой секции — в сокете. У секции с `bind_interface` sing-box держит
`SO_BINDTODEVICE owg1`, и эта привязка переживает перемаршрутизацию. Когда `numgen` уводит такое
соединение на второй луч, маршрут ищется в таблице `51822`, но с ограничением на `owg1`; там его
нет — и пакет доходит до страховки `31502`, где отбрасывается.

Наблюдение, на котором это видно: в `/proc/net/nf_conntrack` записи с `mark=134218240` (это
`0x08000200`, метка второго луча) к `dst=57.144.244.34` висели с `packets=0` **в обе стороны** и без
SNAT — наружу не ушло ничего. PTR этого адреса — `instagram-p42-shv-01-fra5.fbcdn.net`, то есть
секция `wgobf`.

**Симптом при этом маскируется, и это худшая часть находки.** Instagram в тот же момент отдавал
20/20: при весах 90/10 на чужой луч уходила малая доля соединений, а sing-box молча переоткрывал
оборванное. Снаружи дефект выглядит как редкие подвисания, а не как поломка, и найти его можно
только в conntrack.

Страховка сработала ровно так, как задумана (SPEC.md, инвариант 6 балансировщика): трафик умер, но
**не утёк** к провайдеру открытым текстом. Дефект не в ней.

Секции на `bind_interface` небазового луча опасности не представляют, и пилот это тоже показал:
`google` и `wg` сидели на `owg2`, их адрес источника — `10.77.2.2`, под фильтр они не попадают
вовсе. Не балансируются, ходят своим лучом, ничего не теряют. Опасна ровно та секция, чей
`bind_interface` указывает на интерфейс **базового** луча.

### Почему этого не поймали тесты

Две причины, и обе про то, чего стенд не воспроизводит:

1. **`SO_BINDTODEVICE` на стенде нет.** Заглушки `ip` и `nft` знают про метки, правила и таблицы, но
   не про сокет, привязанный к устройству, — а весь дефект в том, что привязка сокета сильнее
   перемаршрутизации.
2. **Промежуточного состояния «часть секций переведена, часть нет» в тестах не было.** Проверялось
   либо всё переведено, либо ничего. Роутер жил именно в промежуточном.

Документация в этом месте была не просто неполна, а неверна: запись 1.3.0 обещала, что секция,
привязанная к другому лучу, «идёт как раньше», INSTALL.md — что она «просто не попадёт в
балансировку, молча, без единой ошибки». Для секции базового луча и то и другое ложь: её трафик
ломается.

### Что сделано: балансировщик отказывается включаться при недоведённом переводе

Контракт:

- `obfmesh-balance check` считает секцию Forkop, чей `bind_interface` указывает на интерфейс
  базового луча, проблемой и называет её по имени. Пока такая секция есть, нуля проблем не получить.
- `obfmesh-balance on` при такой секции пакет **не включает**. Не «предупредить и включить», а
  отказать: `enabled` остаётся `0` (проверка идёт до записи в uci), ни таблицы, ни правил не
  появляется, поведение сети не меняется.
- Отказ стоит не на одном `on`, иначе обойти его можно было бы соседней командой. `apply`
  отказывает и сводит карту весов к базовому лучу, оставляя таблицу, SNAT, правила и страховки уже
  переброшенным соединениям. `weights` заканчивается вызовом `apply` и упирается в тот же отказ:
  веса и `mode = manual` в uci он к тому моменту уже записал, а применить их не сможет. Демон
  проверяет это на **каждом** такте, включая первый после старта, — секцию можно вернуть руками или
  пересозданием конфигурации Forkop прямо на работающей балансировке, — и уходит в мягкую
  остановку, записав причину в лог один раз, а не на каждом такте.
- Защита снимается осознанно, опцией `uci set obfmesh-balance.main.allow_bind_interface=1`; эту
  команду печатает сам текст отказа. Она снимает отказ во всех точках сразу и ничего не чинит:
  соединения названных секций, ушедшие на чужой луч, продолжают гибнуть в страховке. Снятие видно —
  `warn` в логе и отдельная строка в `check`, где секция проблемой быть не перестаёт. Защиту
  снимает только явное `1`, `yes`, `true` или `on`: мусор в опции оставляет её на месте.
- Секция на `bind_interface` небазового луча включению не мешает и по-прежнему называется отдельной
  строкой: она не балансируется, ходит своим лучом и ничего не теряет.

Половинчатое состояние перестало быть вопросом внимательности оператора — штатным путём в него
теперь не попасть.

### Вывод для эксплуатации

**Секции переводятся все сразу.** Все секции Forkop, привязанные к интерфейсу базового луча,
переезжают на его адрес одним заходом: один `uci commit forkop`, один `/etc/init.d/forkop restart`
— и только потом `obfmesh-balance on`. Промежуточное состояние плохо не тем, что балансировка
неполна, а тем, что непереведённые секции базового луча теряют часть трафика.

Секции, прибитые к небазовым лучам, переезжают тем же заходом — не потому, что ломаются, а потому,
что жёсткая привязка секции к лучу и балансировка взаимоисключающи: оставленная секция остаётся вне
раскладки навсегда, её доля полосы балансировщику не достанется, а нагрузку с её луча регулятор
всё равно увидит (INSTALL.md, 3.8.2).

Обратный порядок — сначала снять балансировку, потом возвращать секциям `bind_interface` — остаётся
в силе и по той же причине.

## 1.3.0 — правки obfmesh и новый пакет obfmesh-balance 1.0.0

Новый пакет и две правки в `obfmesh`, без которых пакет не живёт.

Версия поднята во всех четырёх местах из PACKAGING.md, 4.1 — `1.2.0` → `1.3.0`. MINOR, а не PATCH:
поведение `om_rule_del_table` и уборки правил изменилось, и по номеру версии на роутере видно,
сносит этот obfmesh чужие правила в своих таблицах или уже нет. Код сервера не менялся, но версия
у релиза одна на все четыре места; формат бандла тот же, любая пара из 1.2.0 и 1.3.0 работает.

### Зачем

Раскладка 1.2.0 делит по лучам сервисы: секция Forkop прибита к `owg1` или к `owg2` навсегда. Пока
работают обе группы, это те самые 359–373 Мбит/с. Но стоит тяжёлому сидеть в одной группе — её луч
забит, соседний простаивает, и суммарная скорость сваливается к одному лучу, то есть к 180 Мбит/с.
obfmesh-balance делит не сервисы, а отдельные соединения.

### obfmesh-balance 1.0.0 — новый пакет

- **Луч выбирается для соединения, а не для сервиса.** Балансируемые секции Forkop выходят с
  адреса базового луча (`"inet4_bind_address":"10.77.1.2"`), а дальше цепочка nft в `hook output`:
  `numgen random mod 100` → карта весов → метка луча → `ct mark`. Соединение ходит одним лучом до
  конца, метка на каждом пакете восстанавливается из `ct mark`. Правило
  `fwmark 0x{i}00/0xff00 lookup 51820+i` с приоритетом `31000+i` уводит помеченный пакет в таблицу
  своего луча.
  (Жребий заменён счётчиком `numgen inc` по точечной чередующейся карте 24.08.2026 — запись выше.)
- **Переброшенное соединение получает SNAT** в адрес своего луча (`nat hook postrouting priority
  srcnat + 10`). Без него пакет умирает на сервере: у пира в AllowedIPs ровно `10.77.{i}.2/32`, а
  адрес источника ядро выбрало при `connect()`, когда цепочка ещё ничего не решила.
- **Базовый луч не платит ничего** — см. находку 6 ниже.
- **Страховка от утечки: на каждый небазовый луч ставится два правила, а не одно.** `31000+i`
  уводит помеченный пакет в таблицу луча, `31500+i` с тем же селектором и действием `blackhole`
  его отбрасывает. Пока таблица луча жива, до страховки дело не доходит. А как только она опустела
  (`obfmesh` на остановке делает `ip route flush table 51820+i`) или правило луча кто-то снял,
  помеченный пакет раньше проваливался в главную таблицу и уходил в WAN под MASQUERADE — к
  провайдеру открытым текстом. Теперь он отбрасывается: отказ вместо утечки. Мягкая остановка
  страховки не снимает, жёсткая снимает вместе с правилами; подробности и проба на роутере —
  находка 9.
- **Веса считает демон** раз в `interval` секунд по приросту `wg show <iface> transfer`: луч,
  тянущий больше честной доли `100/N`, получает вес пониже. Ограничители — `min_share` (ниже неё
  живой луч не опускается, чтобы не остывал) и `max_step` (предел изменения за такт, он же
  скорость возвращения).
- **Живость судится по изменению сырого `latest-handshakes`, а не по настенному возрасту.**
  Значение сдвинулось с прошлого такта — луч живой; стоит на месте дольше `OMB_HS_MAX` (180 с) по
  **монотонным** часам — мёртвый. Настенные часы в решение не входят: у R3S нет RTC, и приехавший
  NTP объявлял бы мёртвыми все лучи разом при исправных туннелях. Возраст рукопожатия остался для
  человека — колонка `HANDSHAKE` и поле `handshake_age`, — и ещё там, где сравнивать не с чем: на
  первом наблюдении и на пересозданном интерфейсе, где счётчик уехал назад. Второй признак смерти
  — односторонний луч: `tx` растёт, `rx` стоит `OMB_MUTE_TICKS` тактов (3) и `OMB_MUTE_SECS`
  секунд (30) подряд. По одному рукопожатию такой луч держался бы до трёх минут, забирая свою долю
  новых соединений.
- **Лёгший луч получает ноль**, а если живых не осталось — раскладка останавливается **мягко**:
  карта весов сводится к `0-99 : mark_base`, новые соединения идут базовым лучом, как без пакета,
  а таблица, SNAT, правила и страховки остаются. По ним доживают соединения, уже переброшенные на
  небазовые лучи: сбросить им conntrack нечем (находка 8), и снять из-под них SNAT значит подвесить
  каждое.
- **Состав лучей не дублируется формулами**: `index`, `iface`, `source_address` и `table` читаются
  из `obfmesh status --json`. Между чтениями демон следит за сигнатурой адресов на `owg*` и
  перечитывает состав при её смене или раз в 300 секунд — `obfmesh status --json` стоит два
  десятка форков, а такт идёт каждые пять секунд.
- **Пакет ставится выключенным** (`option enabled 0`) и в этом состоянии не создаёт ни таблицы, ни
  правил. CLI: `status [--json]`, `apply`, `weights`, `on`, `off`, `teardown`, `check`, `logs`,
  `version`. `off` — мягко и без потерь, `teardown` — жёстко и сразу, со снятием таблицы, правил и
  страховок; он же зовётся из `prerm` при удалении пакета и из демона, когда мягкое состояние
  выключенного пакета провисело дольше `OMB_SOFT_GRACE` (600 с). `check` существует ровно затем,
  чтобы включение не было прыжком в темноту: он проходит по секциям Forkop, по
  `route.default_mark` в конфигурации sing-box, по пробе `numgen`, по своей таблице, по правилам
  лучей и по их страховкам.
- **Зависимости**: `obfmesh` (1.3.0 или новее), `nftables`, `jsonfilter`, `ip-full` — и ни одного
  `kmod-*`, см. находку 7. Нижнюю границу версии obfmesh `DEPENDS` не выражает, поэтому её
  проверяют `postinst` (предупреждением) и `install-nosdk.sh` (отказом) по `OM_VERSION` из
  `/usr/lib/obfmesh/lib.sh`.

### Правка obfmesh: чужое правило в таблице луча больше не сносится

`om_rule_del_table` принимала таблицу и удаляла **всё**, что в неё смотрит, — включая
`fwmark 0x100/0xff00 lookup 51821 pref 31001`: и правило самого балансировщика, и заворот по метке,
который INSTALL.md (приложение В) предлагает поставить рядом и обещает не трогать. Обещание
нарушалось кодом: первый же `apply` уносил чужое правило молча, а симптом выглядел как «трафик по
метке вдруг пошёл мимо туннеля».

Теперь режим удаления — обязательный аргумент: `<pref>` снимает только правила этого приоритета,
`all` — всё, что смотрит в таблицу. Вызов без режима ничего не удаляет, пишет ошибку и возвращает
1: разрушительное поведение по умолчанию получить нельзя. `om_spoke_rules_sync` считает и чистит
только свой приоритет, `om_spoke_route_teardown` при уходе луча снимает только свою пару. Режим
`all` остался в одном месте — `om_legacy_cleanup` для общей таблицы `51820` схемы 1.1.x, которой
эта версия не пользуется и в которой любое правило ведёт в никуда.

Цена решения, названная явно: `apply.sh` собирает номера таблиц из `ip rule show`, поэтому чужое
правило, смотрящее в таблицу уже несуществующего луча, заставляет obfmesh на каждом `apply`
вызывать teardown вхолостую и писать строку `spoke N is gone`. Одна строка на apply, не на тик
watcher.

### Правка obfmesh: смена rule_pref_base больше не оставляет прежнюю пару навсегда

Побочный эффект предыдущей правки, найденный ревью и воспроизведённый запуском:
`om_spoke_rules_sync 1 owg1 10.77.1.2/30` при `OM_RULE_PREF=32000`, потом та же команда при
`40000` — и в `ip rule show` лежат **обе** пары. Приоритет луча выводится из `rule_pref_base`, а
не хранится, поэтому прежняя пара не попадает уже ни под один расчёт: свой приоритет её не видит,
`om_spoke_route_teardown` снимает тоже только текущий. Раньше её уносил режим `all`, которого
теперь нет. Оставленная пара живёт до перезагрузки и продолжает уводить трафик в тот же луч —
безвредно ровно до тех пор, пока базу не меняли ради того, чтобы освободить приоритеты.

Свои правила obfmesh теперь узнаёт по селектору, а не по приоритету. Форм ровно две, и обе
печатаются `ip rule show` буква в букву: `from <адрес луча> lookup <таблица>` и
`from all oif <устройство> lookup <таблица>`. Сравнивается вся строка целиком, поэтому такое
правило снимается на любом приоритете, а сосед по таблице — балансировщик с его
`fwmark 0x100/0xff00` — не подходит ни под одну форму и остаётся на месте. Удаление идёт полным
селектором (`ip rule del pref 32001 from 10.77.1.2 lookup 51821`), а не одним приоритетом: на
старом приоритете может лежать и чужое правило.

Обратная сторона названа в INSTALL.md (приложение В): правило, дословно совпавшее с одной из двух
форм, obfmesh снимет, чьё бы оно ни было. Свой заворот в луч ставится по метке, а не повторением
адреса луча в `from`.

Один случай остаётся неубираемым и назван прямо: если луч исчез вместе со своим устройством, пока
obfmesh не работал, адрес брать неоткуда — уходит правило по `oif`, а правило по адресу на старом
приоритете остаётся. Снимается руками: `ip rule del pref <старый>`.

### Что проверено на живом роутере

Девять находок, каждая — проверка на боевом NanoPi R3S с работающим Forkop и sing-box 1.12.17.
Записаны затем, чтобы не выяснять их второй раз.

**1. `routing_mark` в исходящем sing-box не работает: метка на сокет не ложится.** Секция
`speedtest` с `{"type":"direct","routing_mark":134218496,"inet6_bind_address":"::"}` и правилом
`pref 31001 fwmark 0x100/0xff00 lookup 51821` дала внешний адрес **37.9.41.16** — адрес
провайдера, мимо туннеля, — при приросте счётчиков `owg1` ровно **0 байт**. Правило при этом
исправно: `ip route get 1.1.1.1 mark 0x8000100` отвечает
`dev owg1 table 51821 src 10.77.1.2 mtu 1400`. Использовать `routing_mark` нельзя.

**2. `inet4_bind_address` работает и стал штатным способом привязки.** Та же секция с
`{"type":"direct","inet4_bind_address":"10.77.1.2"}` дала внешний адрес **45.136.127.10**, прирост
`owg1` — **10 488 байт**, `owg2` — **0**. Ничего нового настраивать не пришлось: сокет уходит с
адреса луча и попадает под штатное правило obfmesh `from 10.77.1.2 lookup 51821`. Отсюда же
следствие, на котором держится весь пакет: решение о луче, принятое **до** `connect()`, само даёт
верный адрес источника, а решение, принятое после (наша цепочка в `hook output`), — нет, и потому
переброшенному соединению обязателен SNAT. С тех пор `speedtest` так и стоит на
`inet4_bind_address` базового луча: при переводе остальных секций её пропускают, а не переписывают
второй раз.

**3. Бит `0x04000000` в метке — бесконечная петля.** Правило Forkop
`pref 105 from all fwmark 0x4000000/0x4000000 lookup forkop` уводит помеченный пакет в таблицу
`forkop`, а она состоит из одной строки `local default dev lo`. Проверено `ip route get`: метка с
этим битом даёт локальный маршрут на `lo`. Бит запрещён абсолютно; диапазон `0x00FF0000` тоже не
трогается — он занят Tailscale в валидаторе Forkop.

**4. `meta mark 0x08000000 return` в цепочке Forkop `mangle_output` — точное сравнение, без
маски.** Цепочка стоит на `type route hook output priority mangle` и первым делом отпускает свой
же трафик sing-box. Отсюда два требования. Наша цепочка обязана стоять **позже**
(`priority mangle + 10`): встать раньше и поменять метку — значит лишить пакет sing-box его
пропуска. И `mark_base` обязан совпадать с `route.default_mark` байт в байт, иначе цепочка `out`
не поймает ни одного пакета. Проверено:
`jsonfilter -i /etc/sing-box/config.json -e '@.route.default_mark'` = `134217728` = `0x08000000`.

**5. Синтаксис карты весов: работает только `typeof`.** `nft -c -f` (v1.1.6) принимает
`typeof numgen random mod 100 : meta mark` с `flags interval` и элементами вида
`0-49 : 0x08000000, 50-99 : 0x08000200`. Отвергнуто и повторять не надо: `type integer : mark` в
объявлении карты и `meta mark set meta mark or numgen … map @weights` (несовпадение типов).
Требование `typeof` в силе, а вот сама форма карты с 24.08.2026 другая (запись выше):
`typeof numgen inc mod 100 : meta mark` без `flags interval` и сто точечных позиций вперемешку
вместо двух сплошных диапазонов.

**6. Базовый луч получает в карте `mark_base`, а не метку с номером.** Метка не меняется — значит
ядро не вызывает `ip_route_me_harder`, не идёт вторая маршрутизация и не нужен SNAT. При раскладке
50/50 половина соединений обходится ровно так же дёшево, как без пакета вообще; платит только та
доля, которую перебросили на остальные лучи.

**7. `kmod-nft-*` на этой прошивке ставить нельзя, и не надо.** Работает ядро **6.1.141** из BSP
FriendlyElec (`uname -r`, `/proc/version` — а не 6.12.94, как решили по именам пакетов), тогда как
`kmod-nft-core`, `kmod-nft-nat` и прочие `kmod-*` в feed прошивки собраны под 6.12.94: vermagic не
совпадает, установка либо не проходит, либо кладёт на флеш модули, которые ядро не загрузит. Ровно
так в августе не встал `kmod-amneziawg`. При этом требовать их незачем — `nft_numgen.ko` лежит в
`/lib/modules/6.1.141/`, `nf_tables` и NAT подняты фаерволом fw4. Из `DEPENDS` балансировщика все
`kmod-*` убраны, а способность ядра сделать нужное проверяется на месте пробой `nft -c -f` с
`numgen` — и в `install-nosdk.sh` перед установкой, и в `obfmesh-balance check` при каждом запуске.
Совет в обоих местах один и тот же дословно: смотреть `/lib/modules/$(uname -r)/nft_numgen.ko`, а
не ставить `kmod-nft-core` — расхождение двух строк сторожит отдельный тест.

**8. Утилиты `conntrack` на роутере нет** (`which conntrack` — пусто). Отсюда контракт остановки
балансировщика: сбросить `ct mark` и записи SNAT нечем, поэтому мягкая остановка не снимает
таблицу, а переводит карту весов на базовый луч целиком — уже переброшенные соединения доживают
своим лучом. Жёсткое снятие таблицы и правил должно об этом предупреждать, и симптом у него не
«обрыв», а зависание: запись conntrack переживает снятие таблицы, `nf_nat` доигрывает сохранённое
отображение `10.77.1.2` → `10.77.2.2` без нашего SNAT, метку из `ct mark` восстанавливать уже
некому, и пакет уходит в `owg1` с источником `10.77.2.2` — у пира `swg1` в AllowedIPs ровно
`10.77.1.2/32`, он его молча дропает. Соединение стоит до таймаута приложения.

**9. `ip rule … blackhole` работает как страховка, но своя на каждый луч.** Проба на живом роутере,
правило снято сразу после:

```
ip rule add pref 31502 fwmark 0x0200/0xff00 blackhole   → принято
печатается как:  31502:	from all fwmark 0x200/0xff00 blackhole

при живом 31002 (fwmark 0x200/0xff00 lookup 51822):
  ip route get 1.1.1.1 mark 0x08000200 → dev owg2 table 51822 src 10.77.2.2
после снятия 31002, при живой страховке:
  ip route get 1.1.1.1 mark 0x08000200 → RTNETLINK answers: Invalid argument   (пакет отброшен)
контроль, метка базового луча:
  ip route get 1.1.1.1 mark 0x08000000 → via 37.9.41.254 dev eth0              (не задета)
```

Одним правилом все лучи не накрыть: `ip rule` сравнивает метку на равенство по маске
(`(rule->mark ^ flow->mark) & mask == 0`), а не «любой ненулевой байт». Проверено —
`fwmark 0xff00/0xff00 blackhole` метку `0x08000200` не ловит. Поэтому страховка своя у каждого
небазового луча, и верхняя граница `rule_pref_base` посчитана по их полосе: `200..31489`, а не
`200..31989`.

### Чего нет и что не проверено

1. **Цепочка не проверялась на боевом трафике.** Что она на `priority mangle + 10` действительно
   видит пакеты после `mangle_output` Forkop и что SNAT переброшенного соединения проходит через
   сервер — проверяется только выкаткой. Синтаксис ruleset и транзакции проверены на роутере через
   `nft -c -f`, но это не то же самое.
   **Закрыто пилотом 23.08.2026** (запись obfmesh-balance 1.1.0 выше): и цепочка, и SNAT работают.
2. **IPv6 не балансируется.** Цепочка `out` ловит `meta nfproto ipv4`, у лучей адреса только
   четвёртой версии.
3. **Балансируется только трафик sing-box** — с меткой `route.default_mark` и адресом источника
   базового луча. Всё, что ходит мимо sing-box или привязано к другому лучу, идёт как раньше;
   `check` называет такие секции отдельно.
   **Неверно для одного случая, вскрыто пилотом 23.08.2026** (запись obfmesh-balance 1.1.0 выше):
   секция, привязанная через `bind_interface` к интерфейсу **базового** луча, имеет тот же адрес
   источника, попадает под фильтр цепочки и теряет ту часть соединений, которую увели на чужой луч.
   С 1.1.0 балансировщик при такой секции не включается.
4. **Нижняя граница версии obfmesh не выражена в пакете.** `DEPENDS` умеет требовать пакет, но не
   его версию: `+obfmesh (>= 1.3.0)` сборочная система ищет как имя пакета. Проверка перенесена в
   `postinst` (предупреждение) и `install-nosdk.sh` (отказ), обе читают `OM_VERSION` из
   `/usr/lib/obfmesh/lib.sh`. Значит, `apk add` на роутере со старым obfmesh пройдёт — с руганью в
   stderr, которую можно не заметить в потоке вывода.
5. **Команды CLI `apply`, `weights`, `on`, `off` не покрыты тестами целиком** — они начинаются с
   проверки на root, а тесты идут не под root. Их внутренности покрыты по отдельности.
6. **Поведение при жёстком снятии стало строже в одном окне.** Раньше пакет с меткой луча 2 при
   пустой таблице `51822`, но живом obfmesh, проваливался до его правила
   `32001: from 10.77.1.2 lookup 51821` и уходил через `owg1` — не утечка, просто не тот луч.
   Теперь его отбрасывает страховка. Это ровно то fail-closed, ради которого она заведена, но в
   этом окне поведение изменилось, и симптом «часть трафика встала» ищется не там, где раньше.
7. **Набор тестов балансировщика не запускается из pytest.** `server/tests/test_client_shell.py`
   знает только `openwrt/obfmesh/tests/run.sh`, поэтому `python -m pytest` новый пакет не трогает:
   его набор запускается руками — `sh openwrt/obfmesh-balance/tests/run.sh` и `dash tests/run.sh`,
   оба дают 149 passed. Проверки `sh -n` и `dash -n` по файлам пакета делаются тоже руками, в
   `run.sh` они не добавлены.
8. **Под BusyBox ash набор не гонялся.** Целевой шелл роутера — именно он, а прогон там означал бы
   выкладку файлов на живую машину. Проверено `sh` (bash в POSIX-режиме) и `dash`; несовместимости
   уровня «`local`, `set --`, подстановки» оба ловят, специфику BusyBox — нет.

## 1.2.0

Схема переделана по результатам замеров на боевых машинах. Два режима агрегации из трёх не
работали в принципе, и это выяснилось не рассуждением, а замером: сервер Ubuntu 24.04
(4 ядра, 45.136.127.10) — роутер FriendlyWrt на NanoPi R3S (4×Cortex-A55, ядро 6.1.141),
между ними провайдер, который душит любой VPN-трафик, кроме замаскированного под STUN.

Вместо трёх режимов — одна симметричная схема: **N независимых лучей**, у каждого свой адрес,
своя таблица маршрутизации и своё правило. Агрегация делается не в ядре, а раскладкой сервисов
по лучам у потребителя.

**Это ломающее изменение формата бандла.** Порядок выката — сначала клиент, потом сервер
(PACKAGING.md, 4.3).

### Что это дало

| Конфигурация | Скорость |
|---|---|
| Один туннель, один обфускатор | 111 Мбит/с |
| Два луча, роутер не настроен | 210 Мбит/с |
| Три луча, роутер настроен | 210–222 Мбит/с |
| **Два луча, роутер настроен** | **359–373 Мбит/с**, четыре замера |
| Один TCP-поток внутри одного луча | ~180 Мбит/с, потолок |

### Удалено

**1. Режим `teql`. Пакетная агрегация поверх WireGuard недостижима.**
`sch_teql` перед отправкой ищет соседа (neighbour) через устройство-слейв, а интерфейсы WireGuard
— это `link/void` с флагом `NOARP`, соседей у них нет. Дисциплина цепляется без единой ошибки, а
пакеты молча исчезают: на всех лучах `tc -s qdisc` показывает `Sent 0 bytes 0 pkt`. Bonding
отказывается честнее: `ip link set owg1 master bond0` → `RTNETLINK answers: Not supported`.
Удалено: режим, зависимости `kmod-sched-teql` и `tc-full`, символ сборки
`CONFIG_PACKAGE_obfmesh_teql`.

**2. Агрегатный адрес и многопутевой обратный маршрут. Режим `ecmp` в прежнем виде не работал.**
Схема «общий адрес `10.77.0.2` на `agg0` (VRF) + `ip route ... nexthop dev owg{i}` на сервере»
убивает трафик: сокет, привязанный к лучу через `SO_BINDTODEVICE`, отбрасывает пакеты, пришедшие
на **другой** луч, а сервер выбирает луч для ответа своим хешем. Симптом — работает ровно один
луч, остальные по нулю, и какой именно, меняется от замера к замеру. Удалено: поле бандла
`agg_address`, сеть `10.77.0.0/24` под него, второй адрес в AllowedIPs каждого пира, обратный
многопутевой маршрут к клиенту, `om_route_live_devs()` и `_return_path_devices()` вместе со всем,
что от них зависело.

**3. Устройство `agg0` и VRF.** Общего интерфейса больше нет: агрегировать нечего, а VRF был нужен
только ему. Удалены зависимость `kmod-vrf`, опции uci `agg_iface` и `agg_address`, перестройка
`agg0` при смене таблицы и все проверки вокруг него.

**4. Настройка `agg_mode` целиком.** Режимов не осталось: схема одна. Удалены поле бандла
`agg_mode`, поле настроек сервера, строка `/usr/bin/obfmesh agg-mode *` из ACL LuCI и секция
«Режим агрегации» в панели. Команда `obfmesh agg-mode` осталась только как диагностика: она ничего
не делает, печатает, почему режимов больше нет, и выходит с кодом 2 — у оператора она в пальцах, и
`unknown command` объясняет меньше. Колонка `agg_mode` в таблице настроек сервера тоже осталась:
она `NOT NULL` без значения по умолчанию, её удаление означало бы пересборку таблицы. Миграция 003
замораживает её на `single`, и ничего её больше не читает.

**5. Опции uci `route_table`, `rule_pref`, `fwmark`.** Единой таблицы туннеля больше нет, поэтому
и единой опции для неё нет. Вместо них — базы `route_table_base` (51820) и `rule_pref_base`
(32000): луч i получает таблицу `база + i` и правило с приоритетом `база + i`. Заворот по метке
теперь ставится своим правилом рядом с obfmesh, потому что метку надо направлять в **конкретный**
луч (INSTALL.md, приложение В).

### Что теперь есть вместо этого

- **Луч i полностью самостоятелен.** Клиент: адрес `10.77.{i}.2/30` на `owg{i}`, таблица
  `51820+i` с единственной строкой `default dev owg{i} mtu 1400`, правило
  `from 10.77.{i}.2 lookup 51820+i pref 32000+i`. Сервер: у пира клиента ровно один адрес в
  AllowedIPs — `10.77.{i}.2/32`. Ни одного адреса, который жил бы больше чем на одном луче, ни
  одного выбора пути ни в одну сторону: асимметрии, на которой погорели обе прежние схемы,
  больше нет физически.
- **Раскладка потребителей по лучам.** Разные секции Forkop привязываются к разным лучам
  (`bind_interface owg1`, `bind_interface owg2`), sing-box — полем `bind_interface` в исходящем,
  всё остальное — `SO_BINDTODEVICE` или привязкой к адресу луча. Это и есть агрегация в реальном
  трафике: суммарная скорость набирается разными сервисами на разных лучах. Раскладка на стороне
  потребителя, obfmesh её не ведёт и при смене числа лучей не переносит (INSTALL.md, 3.7).
- **Настройка роутера переехала в пакет.** `/usr/lib/obfmesh/tune.sh`: обфускаторы прибиваются к
  старшим ядрам (`taskset -p 4`, `taskset -p 8` — CPU2 и CPU3 на R3S), RPS на всех приёмных
  очередях, `net.core.netdev_budget=600`, governor `performance`. Применяется идемпотентно при
  старте и после каждого `apply` — pid обфускаторов меняется, привязку надо ставить заново.
  Раньше это жило ручным костылём поверх пакета и терялось при каждом обновлении молча, а вместе с
  ним 150 Мбит/с из 359. Выключатель — `uci set obfmesh.main.tune=0`.
- **Два луча — значение по умолчанию.** Диапазон 1..10 остался, но третий луч на этом роутере
  проверен и медленнее: 210–222 против 359–373 при загрузке процессора 92–98 %. Больше двух — только
  на более сильном клиенте и только с замером до и после.
- **`/etc/config/obfmesh` в `conffiles` — теперь инвариант SPEC, а не деталь Makefile.**
  Объявление было и раньше, но на бою конфиг обновили копированием файлов мимо пакетного
  менеджера: файл из сборки лёг поверх рабочего, токен пропал, клиент потерял сервер. Симптом
  неочевидный — сервис жив, watcher работает, в логе 401, лучи стоят. В PACKAGING.md, 2.5 записан
  способ обновления и проверка на устройстве (хеш конфига до и после, `.apk-new` рядом).

### Починено по дороге

Всё найдено на ревью переделки, всё воспроизведено, у каждого пункта есть тест либо приведённая
проверка.

- **Привязка к ядрам на роутере с 2 и 3 ядрами делала хуже, чем ничего.** Из настройки `2 3`
  оставались только существующие ядра, и на трёхъядерной машине оба обфускатора получали `cpu2`
  при свободном `cpu1`, на двухъядерной — оба `cpu1`. Теперь список добирается сверху вниз мимо
  `cpu0`, а когда своего ядра каждому не досталось бы (одно ядро на двоих), привязка не делается
  вовсе. `om_cpu_list_norm` получила третий аргумент — число обфускаторов.
- **Уборка teql-дисциплины молча не работала без `tc`.** `tc-full` из зависимостей убран, а
  проверка шла через `tc qdisc show`: без `tc` вывод пустой, и код рапортовал «откатывать нечего»
  на луче, который не отправлял ни байта. Обнаружение переехало на `ip link` (он в зависимостях),
  снятие — на `tc`, а если `tc` нет, устройство удаляется и тот же apply создаёт его заново.
- **Три `tune_*` нельзя было выключить пустым значением, хотя так написано в конфиге.**
  `om_cfg_get` не отличала «не задано» от «задано пустым». Теперь решает код возврата `uci`, а
  опции, где пустое значение бессмысленно (`enabled`, `tune`, `obfuscator_bin`, таймауты),
  нормализуются явно.
- **Утечка секрета: `curl.<pid>.rc` с bearer-токеном и админ-ключом оставался на tmpfs.** Чистил
  его только watcher; `obfmesh sync` и `obfmesh spokes` — нет, а после переиспользования pid файл
  считался принадлежащим живому процессу и не удалялся уже никогда. В CLI добавлен trap.
- **`om_lock_acquire` мог крутиться вечно.** В ветке перехвата протухшего лока `continue`
  выполнялся независимо от результата `mv`, минуя и `sleep`, и счётчик, и таймаут: apply.sh
  занимал ядро на 100 % без единой строки в логе, watcher висел на нём синхронно. Теперь `continue`
  только после удавшегося перехвата, а свои же остатки (`apply.lock.stale.<pid>`, в том числе с
  вложенным `apply.lock`) убираются заранее.
- **Осиротевший обфускатор блокировал луч навсегда.** Личность процесса бралась только из
  pid-файла; после очистки `/var/run` процесс продолжал держать `127.0.0.1:1330i`, и каждый
  следующий старт падал на bind. `om_obf_find` находит его одним `grep -lF` по `/proc/*/cmdline` и
  возвращает pid-файл на место.
- **Статус врал про настройку роутера.** `tuning: applied` печаталось из `state.json`, то есть из
  того, что доложил последний apply. Теперь аффинити проверяется на месте (`om_tune_obf_pinned`),
  а watcher перепроверяет всю настройку раз в десять опросов: сброшенный `rps_cpus` или чужой
  `sysctl -p` стоят измеренных 359 → 210 Мбит/с и больше ничем в этом цикле не ловились.
- **`SIGTERM` не доходил до watcher, пока тот спал.** Trap не выполняется, пока работает
  команда переднего плана, а `stop` ждёт 5 секунд и бьёт `kill -9`, так что штатная уборка
  (fifo, pid-файл, curl-конфиг с токеном) на практике почти не выполнялась. `om_sleep` спит
  фоновым `sleep` под `wait`, который сигнал прерывает.
- **`obfmesh status` печатал пустоту вместо `NO ROUTE`.** `om_route_devs` при пустой таблице не
  печатает пустую строку, а не печатает ничего, и `sed 's/^$/NO ROUTE/'` не срабатывал: самый
  важный симптом выглядел как дырка в строке.
- **`om_json_esc` пропускала управляющие символы.** Один таб в `server_url` делал вывод
  `obfmesh status --json` невалидным, и LuCI падала на `JSON.parse` целиком, а не теряла поле.
- **`om_runtime_init` делал `chmod 700` по `/etc/obfmesh` на каждом проходе watcher** — около 2880
  записей в сутки по каталогу на флеше. Теперь режим сначала читается.
- **`om_log` форкала дважды на вызов даже для подавленного сообщения** — в цикле надзора и в
  обработчике SSE-кадров на процессоре, загруженном на 92–98 %. Уровни разложены в `case` без
  подстановок команд.
- **`--help` обфускатора вызывался без таймаута** под удерживаемым apply-локом: бинарник, который
  вместо справки начинает работать, вешал apply и watcher. Обёрнут в `timeout`, а кеш
  `obf-help.txt` теперь удаляется при `apply.sh --down`.
- **Адрес из бандла подставлялся в `ip addr add` дословно.** Сервер без префикса заставил бы
  переустанавливать адрес на каждом apply; в `desired.tab` кладётся нормализованная форма.
- **`install-nosdk.sh` перезаписывал работающие скрипты поверх.** `cp` по исполняющемуся файлу
  обрывает его посреди — воспроизведено на dash: скрипт кончается на середине и выходит с кодом 0.
  Теперь служба останавливается, файлы кладутся через временное имя и `mv` (rename атомарен,
  работающий процесс держит старый inode), после чего служба поднимается обратно.
- **`option server_url` в пакете больше не содержит боевой адрес.** Файл объявлен conffile, так
  что на настроенном роутере значение переживает обновление, а дефолт пакета не может быть верным
  ни для кого, кроме одной машины.

### Тесты

  ядрам, RPS, sysctl, governor) на поддельных `/sys` и `/proc/sys`, различение «пусто» и «не

### Совместимость

Формат бандла изменился: полей `agg_mode` и `agg_address` в нём больше нет. Клиент 1.1.0 держит
`agg_mode` в списке обязательных и проверяет белым списком `single|ecmp|teql`, поэтому бандл
сервера 1.2.0 он отвергнет целиком и останется на последней принятой конфигурации — то есть на
схеме с `agg0`, которой на сервере уже нет. Клиент 1.2.0 к серверу 1.1.0 подключается: лишние поля
он игнорирует, но сервер при этом продолжает держать в AllowedIPs агрегатный адрес и обратный
многопутевой маршрут, поэтому пара считается временной и только на время выката.

Порядок: клиент → сервер. Откат — обе стороны сразу.

### Что проверить на живых машинах

**Сервер, после выката**

```sh
systemctl restart obfmesh-server
obfmesh-ctl status
wg show swg1 allowed-ips; wg show swg2 allowed-ips   # ровно один /32 у каждого пира
ip route show | grep '10.77.'                        # только подсети swg{i}, без nexthop
ip -4 addr show | grep '10\.77\.0\.' || echo 'агрегатной сети не осталось'
```

**Роутер, после выката**

```sh
obfmesh version                          # 1.2.0
obfmesh status                           # у каждого луча свой адрес и своя таблица
ip route show table 51821                # default dev owg1 mtu 1400
ip rule show | grep 5182                 # from 10.77.{i}.2 lookup 51820+i
ip link show agg0 2>/dev/null && echo 'ОСТАТОК 1.1.0: agg0'
ip route show table 51820 | grep . && echo 'ОСТАТОК 1.1.0: таблица 51820'
grep -c token /etc/config/obfmesh        # конфиг пережил обновление
```

Настройка роутера (ожидание `f` в `rps_cpus` верно для 1.2.0; с 24.08.2026 маска по умолчанию
считается мимо ядер обфускаторов и на R3S равна `3` — запись выше):

```sh
taskset -p "$(cat /var/run/obfmesh/obf-c1.pid)"    # маска 4
taskset -p "$(cat /var/run/obfmesh/obf-c2.pid)"    # маска 8
cat /sys/class/net/eth0/queues/rx-0/rps_cpus       # f
sysctl net.core.netdev_budget                      # 600
```

Скорость — два одновременных потока, каждый в своём луче (по одному ожидается ~180 Мбит/с, суммой
359–373):

```sh
curl --interface owg1 -o /dev/null -s -w 'owg1 %{speed_download} B/s\n' <большой файл> &
curl --interface owg2 -o /dev/null -s -w 'owg2 %{speed_download} B/s\n' <большой файл> &
wait
```

Деградация одного луча: `ip link set dev owg2 down` не должен задевать `owg1` — ни его маршрут, ни
его сессии. Секции потребителя, привязанные к `owg2`, при этом теряют выход, и это ожидаемо:
раскладка живёт у потребителя.

## 1.1.0

Раздел оставлен как история. Агрегатный адрес, VRF `agg0` и режим `teql`, о которых он говорит,
удалены в 1.2.0 — команды проверки из него на текущей версии неприменимы.

Итерация по трём дефектам, снятым с боевых машин, и по восемнадцати замечаниям ревью.
Ни одно изменение не трогает формат бандла: клиент 1.0.0 читает бандл сервера 1.1.0, и наоборот
(новое поле `agg_address` сервер выдавал и раньше).

### Не работало и работает

**1. `ecmp` не пропускал ничего через `agg0`.**
У `agg0` не было собственного адреса. Каждый луч сидел в своей `/30`, поэтому пакет, ушедший через
`owg2`, мог нести адрес отправителя `10.77.1.2`; пир `swg2` разрешает только `10.77.2.2/32`, и
ядро отбрасывало такой пакет до всякого NAT. Через `owg{i}` по отдельности всё ходило, через
`agg0` — тишина.
Сервер выдаёт `agg_address` (`10.77.0.{4k+2}/32`), держит его в `allowed-ips` каждого пира и
ставит к нему обратный многопутевой маршрут; клиент вешает его на `agg0` и делает
преимущественным источником маршрута по умолчанию в таблице `51820`.

**2. `teql` создавал битый обратный маршрут.**
`ip route show` на сервере показывал строку `10.77.1.2` без устройства и без nexthop,
`ip route get 10.77.1.2` резолвился в чужой луч с чужим `src`, и клиент отбрасывал ответ.
`wg.replace_multipath_route()` теперь отказывается выполняться с пустым списком устройств, а
`_verify_route()` перечитывает поставленный маршрут и считает отсутствие nexthop ошибкой прохода,
а не успехом.

**3. Watcher не держал подписку.**
`/usr/lib/obfmesh/watcher.sh: line 1083: can't open /etc/obfmesh/bundle.json` на каждом старте до
первого apply. Причина — редирект `< файл`: несуществующий файл сообщает о себе сам шелл, на
своём stderr, раньше чем `2>/dev/null` перенаправляемой команды получает слово. Чтение файлов
переведено на аргумент команды (`om_file_md5`, `om_pid_cmdline`), `om_uptime` проверяет
`/proc/uptime` встроенным тестом перед чтением.

### Исправлено по итогам ревью

**Клиент, критично**

- Маршрут `ecmp` собирался из желаемого списка лучей, а не из поднявшихся. `om_spoke_apply`
  поднимает интерфейс последним действием, поэтому луч, упавший раньше (enslave в VRF,
  `wg set`, назначение адреса), оставался созданным, но `DOWN`. `ip route replace ... nexthop dev
  owgN` при таком устройстве падает **целиком**: в таблице `51820` не оставалось никакого
  `default`, `om_supervise` видел дрейф, звал apply, тот падал так же — цикл без выхода. Один
  больной луч гасил весь агрегат. Добавлена `om_route_live_devs()`: в маршрут попадают только
  существующие и поднятые устройства — тот же критерий, что у `_return_path_devices()` на сервере.
- Гонка на фиксированном пути `$OM_BUNDLE.new`. Путь был общий для всех процессов: `obfmesh sync`
  и синхронизация по событию SSE обе делали `O_TRUNC` и обе продолжали писать со своего смещения,
  а `mv` публиковал смесь с дырой из NUL-байтов. Проигравший получал ENOENT на своём `mv` и писал
  пользователю «sync failed» после корректной закачки. Промежуточный файл теперь уникален
  (`om_conf_mktemp`, `.bundle.<pid>.XXXXXX` рядом с бандлом).
- `om_tmp_cleanup` сносил `"$OM_RUN_DIR"/tmp.*` целиком, включая файл, в который прямо сейчас
  писал `curl` чужого процесса. `apply.sh` зовёт уборку безусловно при старте и в трапах, и
  ровно это ломало параллельный `obfmesh sync` («bundle is empty or missing»). Имена временных
  файлов теперь несут pid создателя, удаляются только свои и файлы мёртвых процессов.

**Клиент, серьёзно**

- `om_agg_prepare` не сверял таблицу существующего VRF. Таблица зашита в устройство при создании:
  после смены `option route_table` `agg0` продолжал резолвить в старую таблицу, а маршрут по
  умолчанию ложился в новую. Все пробы диагностики читают новую таблицу и показывают здоровье —
  отказ без единой строки в логе. Добавлена `om_agg_vrf_table()`; расхождение перестраивает `agg0`
  и вычищает старую таблицу, `om_supervise` считает его дрейфом.
- Адрес `agg0` зависел от режима: в `single` устройство оставалось без адреса. Переключение режима
  снимало адрес и рвало все привязанные к нему сокеты, а потребитель в `single` был обязан
  догадаться взять `10.77.1.2` с `owg1`. Теперь агрегатный адрес назначается во всех трёх режимах.
  Пустым он остаётся только против сервера, который поля `agg_address` не выдаёт вовсе.
- uci-переопределение `agg_address` молча выигрывало у бандла. Скопированный на второй роутер
  `/etc/config/obfmesh` давал двум клиентам один адрес: сервер держит этот `/32` в `allowed-ips`
  только у одного пира, у второго `wg` молча отбрасывает пакеты по cryptokey routing. Расхождение
  с бандлом теперь пишется предупреждением на каждом apply, с объяснением последствий.
- `om_agg_down` не проверял результат переименования teql-мастера и печатал «released the
  sch_teql master» безусловно. Неудача оставляла `agg0` teql-устройством, `om_agg_prepare vrf`
  видел существующий `agg0` и пропускал создание VRF, а каждый луч падал на enslave — при бодром
  «released» в логе. Результат проверяется, `apply.sh` при неудаче останавливается.
- `om_vrf_available` опиралась на каталог `/sys/module/vrf`, которого нет у ядра с
  `CONFIG_NET_VRF=y`. На таком ядре не поднимался и `single` — единственный режим, который на бою
  работал. Проверка заменена на попытку создать устройство: `modprobe` если модуль, дальше судит
  `ip link add`, а `kmod-vrf` упоминается в сообщении об ошибке. То же для `sch_teql`: признаком
  служит появление устройства `teql0`, а не запись в `/sys/module`.

**Клиент, шум и живучесть**

- Синхронизация по событию SSE не имела ограничителя частоты. Кадр `data:` без разбираемого
  `config_version` — распространённый вариант SSE-кипалайва у прокси — давал полный HTTPS GET
  бандла и строку лога на каждый кадр: десятки запросов в секунду, форк `jsonfilter` на кадр,
  ядро R3S в полке. Введён пол по времени: не чаще одной синхронизации по событию за
  `poll_interval`, отложенная не теряется (поднимается флаг `OM_SYNC_PENDING`).
- Постоянная ошибка сети или авторизации логировалась на каждом тике и без backoff. Для отозванного
  токена это навсегда: при `poll_interval=5` — строка ERROR каждые 5 секунд, ~2900 строк в сутки в
  64-килобайтное кольцо `logd`. Одинаковые коды подавляются (`om_http_error_log`, повтор не чаще
  15 минут), 401/403 и 404 получили подсказку, что с ними делать, синхронизация ушла на backoff
  15→300 с.
- Неприменимый бандл перезапускал apply бесконечно. Самый вероятный первый старт — пакет без
  `wg-obfuscator` — давал 4–6 строк каждые 30 секунд, ~14 тысяч в сутки, плюс полный холостой
  прогон. Добавлен backoff по неудачным apply (новый бандл его сбрасывает — новая конфигурация
  самая вероятная починка) и дедупликация причины дрейфа. `om_bundle_validate` теперь отвергает
  бандл, в котором ни у одного луча нет полного ключевого материала: он проходил проверку,
  сохранялся и потом вечно не применялся. Бандл, где неполон лишь один луч из нескольких,
  принимается по-прежнему — это SPEC, инвариант 5.
- Осиротевший `curl` после SIGKILL watcher не подбирался: новый экземпляр затирал pid-файл, и
  убить старую подписку становилось некому. Обычно её снимает `sse_max_time`, но `curl`,
  заблокированный в `write()` в осиротевший fifo с полным буфером, не тикает по таймеру и висит
  вечно. При старте pid читается, сверяется по `cmdline` и снимается.
- Защита от второго watcher выходила с кодом 0 под `respawn 15 5 0` (бесконечные ретраи): procd
  перезапускал инстанс каждые 5 секунд, и каждый запуск заново сканировал весь `/proc` с форком на
  процесс. Сначала выполняется дешёвая проверка по pid-файлу, полный обход остался запасным путём,
  а перед выходом добавлена пауза в `poll_interval` — темп перезапусков падает с 5 секунд до
  ~35 и с сотен форков до двух.
- `om_runtime_init` вызывался ровно один раз. Если `/var/run/obfmesh` исчезал, `om_mktemp`,
  `om_curlrc_write` и `mkfifo` начинали отказывать навсегда, а процесс с точки зрения procd
  оставался здоровым — тихая смерть без перезапуска. Теперь вызывается в начале каждой итерации
  главного цикла, pid-файл watcher восстанавливается.
- Перехват просроченной блокировки в `om_lock_acquire` не был атомарен: два процесса, одновременно
  решившие, что блокировка протухла, могли снести каталог, только что созданный первым, и оба
  считали себя владельцами. Перехват переделан на переименование каталога (`rename()` атомарен,
  выигрывает ровно один), после захвата pid перечитывается, `om_lock_release` не трогает чужую
  блокировку.

**Сервер**

- `rp_filter` не управлялся вообще, хотя вся схема построена на асимметричных путях. При
  `net.ipv4.conf.all.rp_filter=1` пакет, пришедший на `swg{i}`, которого сейчас нет в обратном
  многопутевом маршруте, отбрасывается ядром до NAT — ровно в окне переключения `ecmp → single` и
  каждый раз, когда луч на секунду ушёл в down. Односторонняя тихая потеря трафика, зависящая от
  sysctl дистрибутива. `reconcile()` выставляет `net.ipv4.conf.swg{i}.rp_filter=2` при каждом
  проходе по лучу. `conf.all` не трогается: ядро берёт максимум из `conf.all` и `conf.<dev>`,
  поэтому значения на интерфейсе достаточно, а остальные интерфейсы хоста не ослабляются.

**Найдено самими тестами**

- `om_uptime` читал `/proc/uptime` редиректом `<` — тем самым способом, против которого в этом же
  файле написан комментарий. На OpenWrt файл есть всегда, поэтому в бою это молчало.

### Изменения, заметные снаружи

1. `agg0` в режиме `single` получает агрегатный адрес (`10.77.0.{4k+2}/32`), которого раньше не
   было, и маршрут по умолчанию получает `src`. Потребители, привязанные по `SO_BINDTODEVICE`,
   изменения не заметят; привязанные по адресу — заметят и начнут работать.
2. Промежуточный файл бандла называется `/etc/obfmesh/.bundle.<pid>.XXXXXX` вместо
   `/etc/obfmesh/bundle.json.new`. `postrm` удаляет оба имени.
3. Конфиг curl называется `/var/run/obfmesh/curl.<pid>.rc` вместо `curl.rc`: общий файл приводил
   к тому, что админский вызов CLI мог уйти без `X-API-Key`, а тик watcher — с ним.
4. При частично неудачном apply маршрут по умолчанию теперь **ставится** по живым лучам, а не
   отсутствует целиком. `obfmesh status` показывает сломанный луч в строке `FAILED`.

### Тесты

- Клиентская половина проекта покрыта впервые: `openwrt/obfmesh/tests/run.sh`, 57 тестов на
  POSIX-sh поверх заглушек iproute2/uci/curl/syslog. Заглушка `ip` отказывает там же, где отказывает
  ядро (`route replace` с nexthop на опущенное устройство), — иначе главный дефект этой итерации
  тест бы не поймал. Проверено обратным способом: на коде до исправления падают 7 тестов из 57.
- Набор запускается и из pytest (`server/tests/test_client_shell.py`), плюс `dash -n` по каждому
  скрипту клиента. `bash` сознательно не подставляется: он проглотит башизм, которого на роутере
  не будет.
- Серверные тесты: `server/tests/test_sysctl.py`, 6 тестов на управление `rp_filter` поверх
  подменённого `/proc/sys`.
- Итого 77 python-тестов (было 69) и 57 shell-тестов.

### Что проверить на живых машинах при выкате

Порядок важен: сервер первым, роутер вторым.

**Сервер, до выката**

```sh
sysctl net.ipv4.conf.all.rp_filter net.ipv4.conf.swg1.rp_filter
```

Запишите значения. После выката `swg{i}` обязан стать `2`; `all` меняться не должен.

**Сервер, после выката**

```sh
systemctl restart obfmesh-server
obfmesh-ctl status
sysctl net.ipv4.conf.swg1.rp_filter net.ipv4.conf.swg2.rp_filter   # оба 2
ip route show | grep '10.77.0.'                                    # dev или nexthop, не голый /32
ip route get 10.77.0.2                                             # src должен быть 10.77.{i}.1
wg show swg1 allowed-ips; wg show swg2 allowed-ips                 # 10.77.0.2/32 у обоих
```

**Роутер, после выката — обязательно в этом порядке**

1. `single` — режим, который сейчас даёт 136 Мбит/с. Он меняется сильнее всех: `agg0` получает
   адрес, которого раньше не было, и маршрут получает `src`. Проверять первым, до `ecmp`:

   ```sh
   obfmesh agg-mode single
   ip -4 addr show agg0                     # 10.77.0.2/32
   ip route show table 51820                # default ... src 10.77.0.2 dev owg1
   curl --interface agg0 -s https://ifconfig.me; echo
   curl --interface agg0 -o /dev/null -s -w 'down %{speed_download} B/s\n' <большой файл>
   ```

   Скорость должна остаться на уровне 136 Мбит/с. Если упала или трафик встал — это единственное
   изменение, которое может задеть работающий режим; откат к прежнему поведению — снять адрес
   (`ip -4 addr del 10.77.0.2/32 dev agg0`) и перечитать маршрут без `src`. Причина будет в том,
   что сервер не отдаёт обратный маршрут к `10.77.0.2` (проверка выше).

2. `ecmp` — главное исправление:

   ```sh
   obfmesh agg-mode ecmp
   ip route show table 51820                # несколько nexthop + src
   curl --interface agg0 -s https://ifconfig.me; echo
   wg show owg1 transfer; wg show owg2 transfer    # растут оба
   ```

3. Деградация одного луча — то, ради чего переделан выбор устройств:

   ```sh
   ip link set dev owg2 down
   sleep 40
   ip route show table 51820                # default остаётся, но только через owg1
   curl --interface agg0 -s https://ifconfig.me; echo     # трафик не должен пропасть
   ip link set dev owg2 up
   sleep 40
   ip route show table 51820                # owg2 вернулся в маршрут
   ```

   Это самый важный сценарий выката: раньше он оставлял таблицу без `default` и уводил watcher в
   бесконечный цикл apply.

4. `teql`:

   ```sh
   obfmesh agg-mode teql
   tc qdisc show dev owg1 | grep teql0
   ip -4 addr show agg0                     # тот же /32, что и в остальных режимах
   ip route show table 51820                # default ... src 10.77.0.2 dev agg0
   ```

5. Переключение туда и обратно `teql → ecmp → teql`: адрес `agg0` не должен исчезать ни на одном
   шаге, `ip link show teql0` между переключениями — устройства быть не должно.

6. Реактивность:

   ```sh
   obfmesh status | grep watcher            # running
   # на сервере: obfmesh-ctl spokes 3
   sleep 40; obfmesh status                 # три луча, руками sync не звали
   logread -e obfmesh | tail -30            # без 'can't open', без повторов каждые 30 с
   ```

7. Одновременный `obfmesh sync` и событие SSE — та самая гонка:

   ```sh
   # на сервере поменять настройку и одновременно на роутере:
   obfmesh sync
   jsonfilter -i /etc/obfmesh/bundle.json -e '@.config_version'   # бандл целый
   ls -la /etc/obfmesh/                                           # .bundle.* не остаётся
   ```

8. Смена `route_table` — сценарий, который раньше молча ломал всё:

   ```sh
   uci set obfmesh.main.route_table=51830; uci commit obfmesh
   /etc/init.d/obfmesh reload; sleep 40
   ip -d link show agg0 | grep 'vrf table'  # 51830
   ip route show table 51830                # default здесь
   ip route show table 51820                # пусто
   curl --interface agg0 -s https://ifconfig.me; echo
   uci set obfmesh.main.route_table=51820; uci commit obfmesh; /etc/init.d/obfmesh reload
   ```

**Чего проверка на этих машинах не покажет**

- Ядро с `CONFIG_NET_VRF=y` (встроенный VRF без `/sys/module/vrf`): на NanoPi R3S модуль
  загружаемый, исправление проверено только тестом.
- Поведение при двух и более клиентах: расхождение `agg_address` между роутерами проверялось
  только тестом.
- `sch_teql`, собранный в ядро.
- Осиротевший `curl`, заблокированный в `write()` в полный fifo: воспроизводится только
  `kill -9` watcher в конкретный момент.
