# Установка obfmesh с нуля

Установка состоит из двух половин: управляющий сервер на Linux и клиент на роутере OpenWrt.
Порядок жёсткий — сначала сервер целиком, потом роутер: клиенту неоткуда взять бандл, пока
сервер не отвечает.

Что читать рядом: [SPEC.md](SPEC.md) — контракт, любое расхождение с ним ошибка;
[DEPLOY.md](DEPLOY.md) — тот же выкат, но пошагово с откатом на каждом шаге, для боевых машин
`45.136.127.10` и `192.168.2.1`; [PACKAGING.md](PACKAGING.md) — как собрать пакеты, которые тут
устанавливаются.

Обозначения те же, что в DEPLOY.md: `[S]` — блок команд выполняется на сервере под root,
`[R]` — на роутере под root.

Ни один шаг на роутере не трогает главную таблицу маршрутизации, firewall и конфигурацию
существующих обходных средств. obfmesh создаёт свои интерфейсы `owg{i}`, свои таблицы маршрутов
`51820+i` и свои правила с приоритетом `32000+i`. Пока потребители не привязаны к лучам
(шаг 3.7), для домашней сети установка незаметна.

Схема с версии 1.2.0 симметрична: **N независимых лучей**, у каждого свой адрес, своя таблица и
своё правило. Ни `agg0`, ни VRF, ни `teql`, ни агрегатного адреса больше нет — почему, написано в
SPEC.md, раздел «Что проверено и отвергнуто».

## 1. Что нужно и как проверить готовность

### 1.1 Сервер

| Что | Зачем | Минимум |
|---|---|---|
| Ubuntu 24.04 / Debian 12, root | systemd-юнит, управление сетевым стеком | — |
| Python | сам сервис | 3.11+ |
| `wireguard-tools`, `iproute2`, `iptables` | `wg`, `ip`, правила NAT | — |
| Модуль ядра `wireguard` | интерфейсы `swg{i}` | в составе ядра ≥5.6 |
| `wg-obfuscator` | обфускация | 1.6+, с поддержкой `masking` |
| Обратный прокси с TLS | публикация API наружу | Caddy или nginx |
| Внешние порты `udp/48201..4820N` | приём лучей | по числу лучей |
| Свободный `tcp/8080` на 127.0.0.1 | API | — |

Проверка `[S]`:

```sh
. /etc/os-release; echo "$PRETTY_NAME"
python3 -V
command -v wg ip iptables systemctl || echo 'ЧЕГО-ТО НЕТ'
modprobe wireguard && ls -d /sys/module/wireguard
ss -lntp | grep -E ':(443|8080)\b' || echo 'порты 443 и 8080 свободны'
```

Ожидается: Python 3.11 и выше, все четыре утилиты на месте, модуль загружается, порты свободны.
Если Python старше — дальше идти нельзя, сервис не запустится.

### 1.2 Роутер

| Что | Зачем |
|---|---|
| OpenWrt/FriendlyWrt 25.12.x, aarch64, procd, BusyBox ash, `apk` | целевая платформа |
| `wireguard-tools`, `kmod-wireguard` | интерфейсы `owg{i}` |
| `curl`, `jsonfilter` | REST, SSE, разбор бандла |
| `ip-full` | `ip rule` и `ip -d link` — в `ip-tiny` их нет |
| `wg-obfuscator` | той же версии, что на сервере |
| ~1 МБ свободной флеш-памяти | пакеты `obfmesh` и `luci-app-obfmesh` |

`kmod-vrf` и `kmod-sched-teql` в 1.2.0 не нужны: общих устройств не осталось, удалять их не
обязательно, но и держать незачем.

`tc-full` — отдельный случай. Зависимостью он больше не является: obfmesh ничего не вешает на
`tc`. Но роутер, обновляемый **с 1.1.0 в режиме `teql`**, приходит с teql-дисциплиной на лучах,
и снять её умеет только `tc`. Обнаруживает её obfmesh через `ip link` (он в зависимостях), а
если `tc` нет — удаляет устройство луча, и тот же apply создаёт его заново уже чистым. Оба пути
рабочие; с `tc` он тише. После первого удачного apply `tc-full` можно снимать.

`taskset` в зависимостях тоже нет, потому что это applet BusyBox на одних сборках и пакет
`util-linux-taskset` на других. Без него привязка обфускаторов к ядрам пропускается — а это
измеренные 359 → 210 Мбит/с, так что проверить стоит: `command -v taskset`.

Необязательный пакет obfmesh-balance (раздел 3.8) добавляет к этому списку `nftables` — и больше
ничего. Ни одного `kmod-nft-*` он не требует, и это сделано намеренно.

**Ловушка, на которой уже обожглись.** На FriendlyWrt работает ядро 6.1.141 из BSP FriendlyElec
(`uname -r`), а пакеты `kmod-*` в её feed собраны под 6.12.94. `apk add kmod-nft-core` либо не
проходит вовсе, либо кладёт на флеш модули, которые это ядро не загрузит: vermagic не совпадает.
Ровно так в августе не встал `kmod-amneziawg`. Ставить `kmod-*` на этой прошивке нельзя, и
незачем: нужные модули уже в образе — `/lib/modules/6.1.141/nft_numgen.ko` лежит на месте, а
`nf_tables` и NAT подняты фаерволом fw4.

Проверяется поэтому не наличие пакета, а способность работающего ядра сделать то, что нужно
(модуль подгружается по требованию):

```sh
uname -r                                       # 6.1.141 — ядро FriendlyElec
ls /lib/modules/$(uname -r)/nft_numgen.ko      # модуль в прошивке
nft -c -f - <<'EOF'
table inet omb_probe {
	chain c {
		meta mark set numgen random mod 100
	}
}
EOF
```

Молчание `nft -c -f` — всё на месте. Ту же пробу делают `install-nosdk.sh` перед установкой и
`obfmesh-balance check` при каждом запуске, причём совет в обоих один и тот же слово в слово:
смотреть `/lib/modules/$(uname -r)/nft_numgen.ko`, а не ставить `kmod-nft-core`.

Проверка `[R]`:

```sh
cat /etc/openwrt_release | head -3; uname -r
apk info -e wireguard-tools kmod-wireguard curl jsonfilter ip-full
ls -l /usr/bin/wg-obfuscator
ip route show table 51821; ip route show table 51822     # должно быть пусто
ip rule show | grep -E '^320[0-9][0-9]:' || echo 'правила свободны'
nproc; df -h /overlay | tail -1
```

Чего не хватает — ставится одной командой:

```sh
apk add ip-full
ip -V; readlink -f /sbin/ip     # ip-full приоритетнее ip-tiny в alternatives
```

`ip-full` и `ip-tiny` в 25.12 сосуществуют: `/sbin/ip` — симлинк, который система alternatives
переключает на `ip-full` (приоритет 300 против 200). Роутер не остаётся без `ip` ни на секунду.

Если таблицы `51821+` или приоритеты `32001+` уже заняты чужими правилами — задайте другие базы
на шаге 3.3 (`route_table_base`, `rule_pref_base`). Чужие маршруты obfmesh не трогает, но и делить
таблицу с кем-то не будет: уборка луча стирает таблицу целиком. Сменить базу можно и потом, на
работающем роутере: со следующим `apply` пара правил переезжает на новые приоритеты, а прежняя
снимается — обе формы obfmesh узнаёт по селектору, а не по номеру.

### 1.3 Обфускатор

`wg-obfuscator` нужен с обеих сторон и в пакеты не входит: путь задаётся настройкой
(`obfuscator_bin` в uci на роутере, `PATCH /api/settings` на сервере).

```sh
wg-obfuscator --version
wg-obfuscator --help | grep -i masking
```

В выводе `--help` обязано быть `masking`, среди значений — `STUN`. Без маскировки провайдер режет
поток, а выглядит это как «туннель поднят, рукопожатие есть, трафика нет». obfmesh проверяет это
сам и отказывается поднимать луч на бинарнике без `masking`.

Значение маскировки должно совпадать на обоих концах байт в байт — обе стороны пишут `STUN`
заглавными.

## 2. Сервер

### 2.1 Бинарник обфускатора

```sh
install -m 0755 wg-obfuscator /usr/local/bin/wg-obfuscator
/usr/local/bin/wg-obfuscator --help | grep -i masking
```

Путь произвольный, но его надо запомнить: он попадёт в настройки.

### 2.2 Управляющий сервис

Два способа, результат одинаковый. Пакет удобнее там, где нужны обновления и удаление одной
командой; `install.sh` — там, где сервер один и ставится из исходников.

**Способ А, пакет** (сборка описана в [PACKAGING.md](PACKAGING.md)):

```sh
OBFMESH_EXTERNAL_HOST=45.136.127.10 \
OBFMESH_OBFUSCATOR_BIN=/usr/local/bin/wg-obfuscator \
apt-get install -y ./obfmesh-server_1.3.0-1_all.deb
```

Обе переменные необязательны и читаются только при первом создании строки настроек. Без
`OBFMESH_EXTERNAL_HOST` адрес определяется по маршруту по умолчанию — на сервере с одним белым
адресом это обычно верно, но проверить стоит (`obfmesh-ctl status`). Изменить потом:
`PATCH /api/settings`.

Postinst создаёт venv, генерирует админ-ключ, включает и запускает юнит. Если Python-зависимости
поставить не удалось (нет сети и нет вшитых wheels), установка честно падает; после починки сети
— `apt-get -f install`.

**Способ Б, из исходников:**

```sh
apt-get install -y wireguard-tools iproute2 iptables python3-venv
cd server
OBFMESH_EXTERNAL_HOST=45.136.127.10 \
OBFMESH_OBFUSCATOR_BIN=/usr/local/bin/wg-obfuscator \
sudo -E ./install.sh
```

`install.sh` идемпотентен: повторный запуск при неизменных исходниках ничего не перезапускает. В
конце он требует, чтобы каждый настроенный луч был поднят, а его обфускатор жив, — то есть
проверяет не «FastAPI стартовал», а «система сошлась».

Смешивать способы не надо: `install.sh` кладёт юнит в `/etc/systemd/system`, а пакет — в
`/usr/lib/systemd/system`, и копия в `/etc` перекрывает пакетную. Postinst об этом предупреждает.

**Проверка** `[S]`:

```sh
systemctl is-active obfmesh-server
obfmesh-ctl status
wg show swg1 | head -5
ss -lunp | grep -E ':(48201|48202)\b'
pgrep -af wg-obfuscator
```

Ожидается: сервис `active`, два луча (значение по умолчанию), у каждого поднят интерфейс и жив
обфускатор, порты слушаются. Если нет — `journalctl -u obfmesh-server -n 80` и
`tail -50 /var/log/obfmesh/obf1.log`.

### 2.3 Что появилось в системе

| Путь | Что | Права |
|---|---|---|
| `/opt/obfmesh` | код и venv | 755 |
| `/etc/obfmesh/admin.key` | админ-ключ, значение нигде не печатается | 600 |
| `/etc/obfmesh/obf{i}.conf` | конфиги обфускаторов, в них ключ обфускации | 600 |
| `/etc/obfmesh/caddy-snippet.txt` | готовый блок для обратного прокси | 644 |
| `/var/lib/obfmesh/obfmesh.db` | настройки, ключи лучей, клиенты | 700 на каталоге |
| `/run/obfmesh/obf{i}.pid` | pid-файлы, по ним обфускаторы подбираются после рестарта | 700 на каталоге |
| `/var/log/obfmesh/obf{i}.log` | логи обфускаторов, ротация `/etc/logrotate.d/obfmesh` | 700 на каталоге |
| `obfmesh-ctl` | локальное управление без HTTP (`/usr/sbin` из пакета, `/usr/local/sbin` из install.sh) | 755 |

Интерфейсы `swg{i}` с адресом `10.77.{i}.1/24`, правила NAT для `10.77.0.0/16` и `ip_forward=1`
создаёт сам сервис при первом `reconcile()`. Никаких маршрутов к клиенту сервер не ставит: адрес
клиента в луче i лежит в `/24` своего `swg{i}` и попадает туда по AllowedIPs.

### 2.4 Публикация наружу

API слушает только `127.0.0.1:8080`. Это не настройка «по желанию»: без обратного прокси роутер до
сервера не достучится, а TLS взять неоткуда.

**Caddy.** Готовый блок лежит в `/etc/obfmesh/caddy-snippet.txt`:

```
45.136.127.10 {
    handle_path /obfmesh/* {
        reverse_proxy 127.0.0.1:8080 {
            flush_interval -1
        }
    }
}
```

`flush_interval -1` обязателен: `/api/events` — потоковый ответ, буферизация превращает
реактивность в опрос раз в 15 минут.

```sh
caddy validate --config /etc/caddy/Caddyfile
systemctl reload caddy
```

**nginx** — если он уже стоит на сервере:

```
location /obfmesh/ {
    proxy_pass http://127.0.0.1:8080/;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_buffering off;
    proxy_read_timeout 3600s;
}
```

Слэш в конце `proxy_pass` обязателен — он срезает префикс `/obfmesh`, как это делает `handle_path`
у Caddy. Панель строит адреса API относительно текущего пути, поэтому с обоими вариантами она
работает без дополнительных настроек. `proxy_buffering off` — то же самое требование, что
`flush_interval -1`.

**Порты обфускаторов.** `udp/48201..4820N` должны быть доступны снаружи. В юните стоит
`OBFMESH_MANAGE_INPUT=1`, и сервис сам вставляет разрешающие правила в INPUT; если правилами
управляете вы, поставьте `0` в drop-in и откройте порты сами.

**Проверка** `[S]`:

```sh
curl -sk -o /dev/null -w '%{http_code}\n' https://45.136.127.10/obfmesh/api/status
# 401 — прокси работает и аутентификация на месте

KEY=$(cat /etc/obfmesh/admin.key)
curl -sk -H "X-API-Key: $KEY" https://45.136.127.10/obfmesh/api/status | head -c 200
```

С третьей машины — что порт обфускатора виден снаружи:

```sh
nc -u -z -w3 45.136.127.10 48201; echo $?
```

и одновременно на сервере `tcpdump -ni any udp port 48201 -c 5`. Пакеты видны — путь есть.

**Сертификат для голого IP.** Caddy выписывает его своим внутренним CA, и curl на роутере ему не
поверит. Корневой сертификат понадобится на шаге 3.2:

```sh
cp /var/lib/caddy/.local/share/caddy/pki/authorities/local/root.crt /root/obfmesh-ca.crt
```

### 2.5 Первый вход в панель

Откройте `https://45.136.127.10/obfmesh/`. Панель спросит админ-ключ — тот самый, что лежит в
`/etc/obfmesh/admin.key`:

```sh
sudo cat /etc/obfmesh/admin.key
```

Галочка «запомнить» кладёт ключ в `localStorage`, без неё — в `sessionStorage` на время вкладки. С
общей машины лучше без галочки.

Три раздела: **Состояние** (лучи, рукопожатия, счётчики), **Настройки лучей** (число лучей,
маскировка, MTU, внешний адрес), **Клиенты**.

### 2.6 Клиент и токен

Через панель: раздел «Клиенты» → имя (латиница, цифры, точка, дефис, подчёркивание) → «Создать».
Токен показывается **один раз**, вместе с готовой строкой `uci set ...` для роутера и кнопкой
скачивания бандла.

То же самое из консоли:

```sh
KEY=$(sudo cat /etc/obfmesh/admin.key)
curl -s -X POST http://127.0.0.1:8080/api/clients \
     -H "X-API-Key: $KEY" -H 'Content-Type: application/json' \
     -d '{"name":"nanopi"}'
```

Токен в открытом виде на сервере не хранится — только его хеш и первые восемь hex-символов
(`token_id`) для сверки «тот ли токен». Потеряли — заведите нового клиента.

Создание клиента сразу прописывает его пиров на все лучи, каждому — ровно один адрес:

```sh
curl -s -H "X-API-Key: $KEY" http://127.0.0.1:8080/api/clients
wg show swg1 allowed-ips        # 10.77.1.2/32 и ничего больше
wg show swg2 allowed-ips        # 10.77.2.2/32 и ничего больше
```

Второй адрес в AllowedIPs пира — след схемы 1.1.0 с агрегатным адресом. На 1.2.0 его быть не
должно; появился — это ошибка реализации, а не настройка.

## 3. Роутер

### 3.1 Пакеты

Сборка описана в [PACKAGING.md](PACKAGING.md). Локально собранные пакеты не подписаны индексом
репозитория, поэтому ставятся с явным `--allow-untrusted`:

```sh
apk add --allow-untrusted ./obfmesh-1.3.0-r1.apk ./luci-app-obfmesh-1.3.0-r1.apk
install -m 0755 wg-obfuscator /usr/bin/wg-obfuscator
/usr/bin/wg-obfuscator --help | grep -i masking
```

Оба пакета — одной командой: у `luci-app-obfmesh` зависимость на `obfmesh`.

Менеджер пакетов включает и запускает сервис сам. Пока не настроены `server_url` и `token`,
watcher только пишет об этом в лог — это ожидаемо.

Если на роутере лежал ручной костыль `/usr/lib/obfmesh/tune.sh` (настройка ядер и RPS поверх
пакета 1.1.0), уберите его вызов из `rc.local`/cron **до** установки: с 1.2.0 этот файл приходит с
пакетом и вызывается самим obfmesh.

**Проверка:**

```sh
ls -l /usr/lib/obfmesh/ /usr/bin/obfmesh      # apply.sh, watcher.sh, tune.sh, lib.sh
obfmesh version
ping -c2 8.8.8.8            # существующий выход в интернет не тронут
```

Обновление с 1.1.0 конфиг не трогает: `/etc/config/obfmesh` объявлен в `conffiles`, менеджер
пакетов кладёт рядом `.apk-new` и оставляет ваш файл с токеном на месте. Проверить, что так и
вышло:

```sh
grep -c token /etc/config/obfmesh      # токен на месте
ls /etc/config/obfmesh*                # obfmesh и, возможно, obfmesh.apk-new
```

### 3.2 Сертификат сервера

Нужен, только если сервер опубликован на голом IP с сертификатом внутреннего CA (шаг 2.4). Для
сертификата от публичного УЦ шаг пропускается: `curl` на OpenWrt использует
`/etc/ssl/certs/ca-certificates.crt`, который приходит вместе с `curl` (зависимость `ca-bundle`).

```sh
scp root@45.136.127.10:/root/obfmesh-ca.crt /etc/obfmesh/server-ca.crt
chmod 600 /etc/obfmesh/server-ca.crt
```

### 3.3 Настройка

```sh
uci set obfmesh.main.server_url='https://45.136.127.10/obfmesh'
uci set obfmesh.main.token='<токен из 2.6>'
uci set obfmesh.main.obfuscator_bin='/usr/bin/wg-obfuscator'
uci set obfmesh.main.ca_file='/etc/obfmesh/server-ca.crt'
uci commit obfmesh
```

Полный список опций с умолчаниями — в приложении В и в комментариях `/etc/config/obfmesh`.

Прежде чем запускать сервис, проверьте, что сервер вообще виден:

```sh
curl --cacert /etc/obfmesh/server-ca.crt -s -o /dev/null -w '%{http_code}\n' \
     https://45.136.127.10/obfmesh/api/status
# 401 — сервер отвечает и сертификат принят
```

`000` — не достучались (адрес, маршрут, firewall). `60` в тексте ошибки curl — сертификат не
принят: не тот CA-файл. Временный обход `uci set obfmesh.main.tls_insecure=1` открывает канал
управления для перехвата, поэтому годится только как способ диагностики.

### 3.4 Первый запуск

```sh
/etc/init.d/obfmesh restart
sleep 15
obfmesh status
```

Что должно быть в выводе:

- `config_version` не пустой, применён секунды назад;
- по каждому лучу `LINK up`, `OBFUSC ok:<pid>`, `HANDSHAKE` меньше двух минут, свой адрес
  `10.77.{i}.2/30`, своя таблица `51820+i`;
- `watcher: running`;
- строки `FAILED` нет;
- в полях `token` и `obfuscation key` — `<есть>`. Значений секретов в выводе быть не должно; если
  значение видно, это ошибка, а не особенность.

### 3.5 Проверка, что трафик ходит

Пока — не трогая домашнюю сеть, а привязываясь к лучу явно:

```sh
ping -c3 -I owg1 10.77.1.1                 # адрес сервера в первом луче
ping -c3 -I owg2 10.77.2.1

curl --interface owg1 -s https://ifconfig.me; echo
curl --interface owg2 -s https://ifconfig.me; echo
# оба должны ответить внешним адресом сервера

wg show owg1 transfer; wg show owg2 transfer
ip -4 addr show owg1                       # 10.77.1.2/30
ip route show table 51821                  # default dev owg1 mtu 1400
ip rule show | grep 5182                   # from 10.77.{i}.2 lookup 51820+i
```

Замер по одному лучу:

```sh
curl --interface owg1 -o /dev/null -s -w 'down %{speed_download} B/s\n' \
     https://speed.hetzner.de/100MB.bin
```

Ожидаемый порядок для одного луча — около 180 Мбит/с (22 МБ/с). Суммарные 359–373 Мбит/с
получаются двумя такими замерами одновременно, каждый со своим `--interface`:

```sh
curl --interface owg1 -o /dev/null -s -w 'owg1 %{speed_download} B/s\n' \
     https://speed.hetzner.de/100MB.bin &
curl --interface owg2 -o /dev/null -s -w 'owg2 %{speed_download} B/s\n' \
     https://speed.hetzner.de/100MB.bin &
wait
```

Один поток по двум лучам не раскладывается — это свойство схемы, а не поломка (SPEC, «Что
проверено и отвергнуто», п. 4).

### 3.6 Настройка роутера

Без неё два луча дают 210 Мбит/с вместо 359–373. С 1.2.0 она приезжает с пакетом
(`/usr/lib/obfmesh/tune.sh`) и применяется идемпотентно при старте сервиса и после каждого
`apply` — pid обфускаторов меняется, привязку надо ставить заново.

Что делается:

1. Обфускаторы прибиваются к старшим ядрам, чтобы не драться за такты с сетевым softirq: на
   4-ядерном R3S с двумя лучами это CPU2 и CPU3 (`taskset -p 4 <pid1>`, `taskset -p 8 <pid2>`).
2. RPS на всех приёмных очередях физических интерфейсов:
   `echo f > /sys/class/net/<dev>/queues/rx-*/rps_cpus`.
3. `sysctl net.core.netdev_budget=600`.
4. Governor `performance` на всех ядрах.

Проверка `[R]`:

```sh
taskset -p "$(cat /var/run/obfmesh/obf-c1.pid)"    # current affinity mask: 4
taskset -p "$(cat /var/run/obfmesh/obf-c2.pid)"    # current affinity mask: 8
cat /sys/class/net/eth0/queues/rx-0/rps_cpus       # f
sysctl net.core.netdev_budget                      # 600
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor   # performance
```

Выключается настройкой `uci set obfmesh.main.tune=0` — например, если ядра распределяет другой
сервис. Тогда 359 Мбит/с ждать не стоит: измерения выше сняты с ней.

Числа рассчитаны на 4 ядра R3S: обфускаторы на старших ядрах, сетевой softirq на младших. На
другом железе их надо пересчитать под своё число ядер, иначе прирост не воспроизведётся.

### 3.7 Разведение сервисов по лучам

Первый шаг, который реально влияет на домашнюю сеть. Делайте, когда предыдущие пункты стабильно
отработали хотя бы сутки.

Именно здесь и получается агрегация. Ядро один поток по лучам не раскладывает, поэтому суммарная
скорость набирается тем, что **разные сервисы уходят в разные лучи**. Раскладка живёт у
потребителя, одной строкой на секцию.

Перед началом — снимок конфигурации:

```sh
cp /etc/config/network /etc/config/network.before-obfmesh
( umask 077; uci show forkop > /root/forkop.before-obfmesh 2>/dev/null )
chmod 600 /root/forkop.before-obfmesh
ls -l /root/forkop.before-obfmesh          # -rw-------
```

**Снимок Forkop — файл с секретом.** В `uci show forkop` попадает `subscription_urls` секции,
которая работает по подписке, а это URL с токеном прямо в пути: у кого он есть, тот пользуется
подпиской. Поэтому снимок остаётся на роутере в `/root` и никуда больше: не копируется на рабочую
машину, не кладётся в `/www` (этот каталог отдаётся наружу через проброс 11228) и не вставляется
в переписку. `umask 077` работает только на создание файла — если он уже лежал, права останутся
прежними, поэтому рядом стоит `chmod`.

**Forkop.** Каждая секция привязывается к своему лучу. Смотрим, что есть, и разводим:

```sh
uci show forkop | sed -E "s/^([^=]*(urls?|token|key|secret|password|uuid))=.*/\1='<есть>'/" |
	grep -E 'bind_interface|=.*section'

uci set forkop.<секция_1>.bind_interface='owg1'
uci set forkop.<секция_2>.bind_interface='owg1'
uci set forkop.<секция_3>.bind_interface='owg2'
uci set forkop.<секция_4>.bind_interface='owg2'
uci commit forkop
/etc/init.d/forkop restart
```

Привязка бывает в двух формах: отдельной опцией секции, как в примере выше, и полем
`bind_interface` внутри `outbound_json`. Какая стоит сейчас, видно в выводе первой команды; менять
надо ту, что уже есть, а не заводить вторую рядом. Сколько секций и как они называются — вопрос к
своему роутеру, а не к этому документу: цикл, печатающий состав целиком, есть в 3.8.2.

`sed` в этой команде подменяет значения секретных опций на `<есть>` — тот же маркер, каким obfmesh
показывает наличие токена в своих отчётах. Замаскированный вывод не страшно вставить в переписку;
без маски туда уедет URL подписки с токеном в пути.

**sing-box.** То же самое полем исходящего:

```json
{
  "outbounds": [
    {"type": "direct", "tag": "via-owg1", "bind_interface": "owg1"},
    {"type": "direct", "tag": "via-owg2", "bind_interface": "owg2"}
  ]
}
```

**Что угодно ещё** — `SO_BINDTODEVICE` (`curl --interface owg1`) либо привязка к адресу
`10.77.{i}.2`: правило `from 10.77.{i}.2 lookup 51820+i` уведёт такой сокет в нужный луч.

Правила раскладки:

1. Один сервис — один луч. Размазывать один сервис по двум лучам смысла нет: его поток всё равно
   упрётся в 180 Мбит/с в том луче, куда попал.
2. Делить по нагрузке, а не по алфавиту: тяжёлое (видео, загрузки) — на один луч, разговорчивое и
   мелкое (мессенджеры, API) — на другой.
3. Число лучей и раскладка связаны вручную. Уменьшили число лучей на сервере — секции, привязанные
   к исчезнувшему интерфейсу, останутся без выхода, пока их не перевесят.

**Проверка:**

```sh
wg show owg1 transfer; wg show owg2 transfer     # растут оба, когда работают обе группы
curl -s https://ifconfig.me; echo                # с клиента домашней сети
obfmesh status
```

**Откат.** Вернуть потребителям прежний выходной интерфейс и перезапустить их. Раскладка обратима
целиком: obfmesh при этом не трогается.

### 3.8 Балансировка соединений по лучам (пакет obfmesh-balance)

Шаг необязательный, и ставится он отдельным пакетом. В 3.7 по лучам разводятся сервисы, здесь —
отдельные соединения: все балансируемые секции Forkop выходят с адреса одного луча, а каким лучом
пойдёт конкретное соединение, решает цепочка nft. Смысл в том, что тяжёлая секция перестаёт забивать свой
луч в одиночку, пока соседний простаивает.

Как это работает изнутри — SPEC.md, раздел «Балансировка соединений по лучам». Здесь порядок
действий.

**Перед началом.** Лучи живые (3.5), obfmesh отработал хотя бы сутки, sing-box метит свои сокеты —
на FriendlyWrt с Forkop это значение по умолчанию:

```sh
jsonfilter -i /etc/sing-box/config.json -e '@.route.default_mark'
# 134217728 — это 0x08000000, оно же mark_base пакета
```

#### 3.8.1 Пакет

```sh
apk add --allow-untrusted ./obfmesh-balance-1.0.0-r1.apk
obfmesh-balance version
obfmesh-balance check          # пакет ещё выключен и ничего не делает
```

Зависимости: `obfmesh`, `nftables`, `jsonfilter`, `ip-full` — и ни одного `kmod-*`, почему именно
так, написано в 1.2. Без SDK ставится тем же способом, что и obfmesh:
`sh openwrt/obfmesh-balance/install-nosdk.sh` из распакованных исходников.

**obfmesh нужен от 1.3.0.** Более старый снимает правила `31000+i` на каждом своём `apply`, считая
их чужими в своих таблицах. Пакетный менеджер этого не проверит — указать нижнюю границу версии в
`DEPENDS` нечем, — поэтому проверяют `postinst` (предупреждением) и `install-nosdk.sh` (отказом):

```sh
obfmesh version | head -1        # obfmesh 1.3.0 или новее
```

Пакет приходит выключенным (`option enabled 0`) и в этом состоянии не создаёт ни одной строки в
nft и ни одного `ip rule`. Знаком `?` со словами «что при выключенном пакете и ожидается» `check`
помечает ровно три вещи, и только их: отсутствие таблицы, отсутствие правила луча и отсутствие его
страховки. Всё остальное считается проблемой независимо от того, включён пакет или нет:

- `nft` не принимает `numgen` — карта весов не соберётся ни при каких настройках;
- состав лучей неизвестен: `obfmesh status --json` не отвечает либо `base_spoke` нет среди его
  лучей (эта строка обрывает проверку — дальше смотреть не на чем);
- ни одного живого луча;
- в конфигурации sing-box нет `route.default_mark` или он не совпадает с `mark_base`;
- секция Forkop сидит на `routing_mark` или на `bind_interface`;
- таблица всё-таки есть, а карта весов в ней пуста — весь трафик идёт базовым лучом.

Последняя строка на свежей установке не появляется: таблицы ещё нет. Она для случая, когда пакет
выключили, а таблица осталась мягкой остановкой, и кто-то опустошил карту руками.

#### 3.8.2 Секции Forkop переезжают на адрес базового луча

`bind_interface` для балансировки не годится: устройство выбирается до `connect()`, а цепочка
живёт в `hook output`, то есть уже после. Секция на `bind_interface` просто не попадёт в
балансировку и останется прибитой к своему лучу — молча, без единой ошибки.

`routing_mark` не годится тоже, и это проверено на живом роутере: метка на сокет не ложится,
трафик уходит к провайдеру мимо туннеля (SPEC.md, «Что проверено и отвергнуто», п. 5).

Работает `inet4_bind_address`: сокет уходит с адреса базового луча и попадает под штатное правило
obfmesh `from 10.77.1.2 lookup 51821`, а дальше его подхватывает балансировщик.

Снимок до правки и состав секций — свой, с этой машины и на сегодня. Список секций живёт в Forkop и
меняется без нас, поэтому переписывать его в документ бессмысленно: смотрим то, что есть сейчас.

```sh
( umask 077; uci show forkop > /root/forkop.before-balance )
chmod 600 /root/forkop.before-balance
ls -l /root/forkop.before-balance          # -rw-------

# все включённые секции: подлежит ли переводу, имя, исходящий, привязка отдельной опцией
for s in $(uci -q show forkop | sed -n 's/^forkop\.\([A-Za-z0-9_]\{1,\}\)=section$/\1/p'); do
	[ "$(uci -q get "forkop.$s.enabled" 2>/dev/null)" = 0 ] && continue
	oj="$(uci -q get "forkop.$s.outbound_json" 2>/dev/null)"
	bi="$(uci -q get "forkop.$s.bind_interface" 2>/dev/null)"
	if [ -n "$oj" ]; then mark='перевод'
	elif [ -n "$bi" ]; then mark='руками'
	else mark='пропуск'
	fi
	printf '%s\t%s\t%s\tbind_interface=%s\n' "$mark" "$s" "$oj" "$bi"
done
```

Снимок здесь тот же файл с секретом, что и в 3.7: `subscription_urls` с токеном в пути, права
`600`, живёт только в `/root` на роутере. В `/www`, на рабочую машину и в переписку он не уезжает.

Цикл перебирает секции ровно так же, как это делает `check`: выключенные (`enabled 0`) пропускает,
остальные показывает целиком. Привязка бывает в двух местах — внутри `outbound_json` и отдельной
опцией секции, — и различать их надо: одного `uci show forkop | grep bind_interface` мало, он
находит обе формы вперемешку, а снимать их нужно по-разному. Опция секции снимается тем же заходом,
до `commit`: `check` считает секцию с `bind_interface` небалансируемой и говорит об этом отдельной
строкой.

Первая колонка отвечает на вопрос, подлежит ли секция переводу, и это главное, что из вывода надо
вынести. Включённая секция не значит переводимая:

- `перевод` — у секции есть `outbound_json`, то есть луч выбирается внутри него. Такую разбирает
  второй цикл; уже переведённые он пропустит сам.
- `пропуск` — `outbound_json` у секции нет вовсе и `bind_interface` отдельной опцией тоже нет: ни
  к какому лучу она не привязана, переводить в ней нечего. Так выглядит секция, работающая по
  подписке: узел ей приходит извне, а не из нашей конфигурации.
- `руками` — `outbound_json` нет, но стоит опция `bind_interface`: к лучу секция привязана, а
  шаблона исходящего, из которого можно взять тег, у неё нет. Второй цикл такую не трогает и
  называет отдельной строкой.

Когда пакет уже стоит, тот же состав, но с вердиктом по каждой секции, печатает

```sh
obfmesh-balance check | grep 'секция '     # балансируется / прибита к лучу / мимо лучей вообще
```

Пример вывода первого цикла — боевой NanoPi R3S, снято 22.08.2026: семь включённых секций, из них
шесть с `outbound_json`. Это образец формата, а не чек-лист: на другой машине и в другой день
состав другой.

```
пропуск	proxysvc		bind_interface=
перевод	google	{"type":"direct","tag":"google-out","bind_interface":"owg2"}	bind_interface=
перевод	wg	{"type":"direct","tag":"wg-out","bind_interface":"owg2"}	bind_interface=
перевод	apple	{"type":"direct","tag":"apple-out","bind_interface":"owg1"}	bind_interface=
перевод	wgobf	{"type":"direct","tag":"wgobf-out","bind_interface":"owg1"}	bind_interface=
перевод	speedtest	{"type":"direct","tag":"speedtest-out","inet4_bind_address":"10.77.1.2"}	bind_interface=
перевод	kinopub	{"type":"direct","tag":"kinopub-out","bind_interface":"owg1"}	bind_interface=
```

Здесь же видно, зачем нужен живой вывод, а не список из документа. `proxysvc` — секция на подписке
VLESS: узлы ей приходят из `subscription_urls`, `outbound_json` у неё нет, ни к какому лучу она не
привязана, поэтому и стоит `пропуск`. Секция `kinopub` (домены `kino.pub`, `service-kp.com`) на
`owg1` — её в прежнем списке этого раздела не было вовсе, а переводить её надо наравне с
остальными. А `speedtest` уже сидит на `inet4_bind_address` базового луча: он переведён раньше, при
проверке `routing_mark` (SPEC.md, «Что проверено и отвергнуто», п. 5), и трогать его второй раз
нечего — второй цикл такую секцию пропустит сам, хотя в первом она помечена `перевод`.

Команды перевода под свой состав печатает второй цикл. Он ничего не меняет — только складывает
строки, которые останется прочитать и выполнить:

```sh
BASE=10.77.1.2                                   # адрес базового луча, см. base_spoke в 3.8.5
for s in $(uci -q show forkop | sed -n 's/^forkop\.\([A-Za-z0-9_]\{1,\}\)=section$/\1/p'); do
	[ "$(uci -q get "forkop.$s.enabled" 2>/dev/null)" = 0 ] && continue
	oj="$(uci -q get "forkop.$s.outbound_json" 2>/dev/null)"
	bi="$(uci -q get "forkop.$s.bind_interface" 2>/dev/null)"
	if [ -z "$oj" ]; then
		if [ -n "$bi" ]; then
			printf '# %s: outbound_json нет, только bind_interface=%s — переводить руками\n' "$s" "$bi"
		else
			printf '# %s: ни outbound_json, ни bind_interface — к лучам не привязана, не трогаем\n' "$s"
		fi
		continue
	fi
	if [ "$(jsonfilter -s "$oj" -e '@.type' 2>/dev/null)" != direct ]; then
		printf '# %s: не type=direct — шаблон не подходит, руками\n' "$s"
		continue
	fi
	if [ "$(jsonfilter -s "$oj" -e '@.inet4_bind_address' 2>/dev/null)" = "$BASE" ] && [ -z "$bi" ]; then
		printf '# %s: уже на адресе базового луча — не трогать\n' "$s"
		continue
	fi
	printf 'uci set forkop.%s.outbound_json='\''{"type":"direct","tag":"%s","inet4_bind_address":"%s"}'\''\n' \
		"$s" "$(jsonfilter -s "$oj" -e '@.tag' 2>/dev/null)" "$BASE"
	if [ -n "$bi" ]; then
		printf 'uci -q delete forkop.%s.bind_interface\n' "$s"
	fi
done
```

Секцию, которая уже вышла на адрес базового луча, цикл пропускает со строкой-комментарием — на том
же роутере это `speedtest`, и повторно его никто не переписывает. Из прежнего JSON переносится
только `tag`; любое другое поле — скажем, `inet6_bind_address` — потеряется, поэтому вывод надо
сверить со снимком `/root/forkop.before-balance`, прежде чем выполнять. Секции не с `type: direct`
цикл не трогает и называет их отдельно: шаблон исходящего у них другой.

Секции без `outbound_json` он тоже только называет, и строки у них разные — ровно по колонке
первого цикла. `пропуск` (на этом роутере `proxysvc`) — «к лучам не привязана, не трогаем», и
делать с ней нечего. `руками` — «переводить руками»: луч у секции выбран, а шаблона исходящего,
из которого взялся бы тег, нет, и писать его придётся самому.

Дальше — выполнить отобранные строки и закрыть правку:

```sh
# ...сюда вставляются строки, напечатанные циклом и проверенные глазами...

uci commit forkop
/etc/init.d/forkop restart
```

Теги (`"tag"`) сохраняются как были: на них ссылаются правила маршрутизации sing-box, и
переименование тега рвёт секцию вернее, чем неверная привязка.

**Перезапуск Forkop обязателен и он рвёт соединения.** sing-box перечитывает конфигурацию только
при старте: без `/etc/init.d/forkop restart` новый `outbound_json` не применяется вообще, а с ним
все текущие соединения через прокси обрываются — звонок кладётся, загрузка начинается заново.
Делайте это в тихое время.

Отсюда и порядок внутри блока: правки складываются все сразу, `commit` и `restart` идут последними
и ровно один раз. Опция, снятая после рестарта, не подействует до следующего — а следующий стоит
ещё одного обрыва всех соединений через прокси.

Что получилось — видно до включения балансировщика:

```sh
uci show forkop | sed -E "s/^([^=]*(urls?|token|key|secret|password|uuid))=.*/\1='<есть>'/" |
	grep bind_interface || echo 'привязок по интерфейсу не осталось'
obfmesh-balance check                                         # ни одной строки ПЛОХО про секции
```

Между перезапуском Forkop и включением балансировщика все переведённые секции идут одним лучом —
базовым. Это рабочее, но медленное состояние (один луч — около 180 Мбит/с), поэтому два следующих
шага делаются подряд.

#### 3.8.3 Включение

```sh
obfmesh-balance check          # ноль проблем — можно включать
obfmesh-balance on             # enabled = 1 и сразу применить
/etc/init.d/obfmesh-balance enable
/etc/init.d/obfmesh-balance start
obfmesh-balance status
```

`check` проходит по секциям Forkop и говорит про каждую, балансируется она или нет; `bind_interface`
и `routing_mark` он показывает как проблему с объяснением, чем их заменить.

#### 3.8.4 Проверка

```sh
nft list table inet obfmesh_balance            # карта весов, цепочки out/pick/post
ip rule show | grep -E '^310[0-9][0-9]:'       # fwmark 0x200/0xff00 lookup 51822 у второго луча
ip rule show | grep -E '^315[0-9][0-9]:'       # его страховка: тот же селектор, blackhole
obfmesh-balance status                         # колонки WEIGHT и KERNEL должны совпадать
wg show owg1 transfer; wg show owg2 transfer   # растут оба, а не один
obfmesh-balance logs -n 50
```

Колонка `WEIGHT` — что насчитал регулятор, `KERNEL` — что реально лежит в карте nft. Расхождение
значит, что демон не работает или последняя транзакция nft не прошла.

Правил на небазовый луч два, и второе важно не меньше первого:

```
31002:	from all fwmark 0x200/0xff00 lookup 51822
31502:	from all fwmark 0x200/0xff00 blackhole
```

Пока таблица `51822` жива, работает первое. Как только она опустела или правило `31002` кто-то
снял, помеченный пакет доходит до второго и отбрасывается — вместо того чтобы провалиться в
главную таблицу и уйти в WAN под MASQUERADE, к провайдеру открытым текстом. Проверено на роутере:
при живом `31002` команда `ip route get 1.1.1.1 mark 0x08000200` отвечает
`dev owg2 table 51822 src 10.77.2.2`, без него при живой страховке — `RTNETLINK answers: Invalid
argument`. Метка базового луча не задета: `ip route get 1.1.1.1 mark 0x08000000` по-прежнему даёт
`via 37.9.41.254 dev eth0`.

Если счётчики растут только у базового луча, а правил `31000+i` нет — смотрите, не снёс ли их
кто-то ещё: их держит демон, и он вернёт их на следующем такте. Если пропал не только правило, но и
страховка, помеченный трафик успел уйти мимо туннеля — `obfmesh-balance check` говорит об этом
отдельной строкой.

#### 3.8.5 Настройки

Полный список — приложение Г. Три, которые трогают чаще остальных:

```sh
uci set obfmesh-balance.main.base_spoke='1'    # адрес этого луча стоит в секциях Forkop
uci set obfmesh-balance.main.mode='auto'       # auto | manual | off
uci set obfmesh-balance.main.interval='5'      # период такта регулятора, секунды
uci commit obfmesh-balance
/etc/init.d/obfmesh-balance reload
```

Ручные веса — одной командой, она же переводит `mode` в `manual`:

```sh
obfmesh-balance weights 1:70 2:30
```

**Смена `base_spoke` — это и правка секций Forkop.** Адрес в `inet4_bind_address` обязан быть
адресом базового луча, иначе цепочка `out` не поймает ни одного пакета: секции продолжат ходить
своим лучом, а балансировка тихо перестанет работать.

#### 3.8.6 Откат

Балансировка снимается в двух режимах, и выбор между ними — это выбор, дать ли дожить соединениям,
уже переброшенным на небазовые лучи.

**Мягко, без потерь.** Карта весов переводится на базовый луч целиком (`0-99 : mark_base`),
таблица, правила лучей и их страховки остаются в ядре. Новые соединения идут базовым лучом, то
есть ровно как без пакета; уже переброшенные доживают своим лучом — метка каждого пакета
восстанавливается из `ct mark`, SNAT на месте. Это режим штатной остановки: так работают
`obfmesh-balance off`, `mode = off`, `enabled = 0` и `/etc/init.d/obfmesh-balance stop`.

**Жёстко.** Таблица, правила `31000+i` и страховки `31500+i` уходят целиком. Соединение, уже
переброшенное на небазовый луч, после этого не рвётся, а **виснет** — и знать это надо заранее,
иначе симптом не опознать. Запись conntrack переживает снятие таблицы, `nf_nat` доигрывает
сохранённое отображение `10.77.1.2` → `10.77.2.2` уже без нашего SNAT, а восстанавливать метку из
`ct mark` больше некому: цепочек нет. Пакет уходит штатным путём базового луча, в `owg1`, но с
источником `10.77.2.2` — у пира `swg1` в AllowedIPs ровно `10.77.1.2/32`, и он молча его дропает.
Ни ответа, ни отказа: соединение стоит до таймаута приложения. Режим нужен, когда след пакета надо
убрать из ядра прямо сейчас; молча он не выполняется, команда предупреждает.

Мягкое — не «аккуратный вариант жёсткого», а единственный способ уйти без потерь: привязка
соединения к лучу живёт в `ct mark` и в записи SNAT внутри conntrack, а сбросить их нечем —
утилиты `conntrack` на этом роутере нет (`which conntrack` — пусто).

**Мягкое состояние переходит в жёсткое само, но только пока работает демон.** Выключенный пакет не
имеет права держать своё на роутере вечно: пролежав `OMB_SOFT_GRACE` секунд (по умолчанию 600 —
типичный idle-таймаут прикладного соединения) при `enabled = 0` или `mode = off`, демон снимает
таблицу, правила и страховки сам. Отсчёт идёт в его цикле, поэтому убитый демон отсчитывать нечем:
после `stop` мягкое состояние живёт до перезагрузки или до явного `teardown`. Порядок отката из
этого и следует.

Штатно — дать переброшенным соединениям дожить:

```sh
obfmesh-balance off                            # мягко; Forkop не трогать
                                               # демон НЕ останавливать: он и снимет остальное
sleep 660                                      # OMB_SOFT_GRACE 600 с плюс такт демона
ip rule show | grep -E '^31[05][0-9][0-9]:' || echo 'правил и страховок нет'
nft list table inet obfmesh_balance 2>/dev/null || echo 'таблицы нет'
/etc/init.d/obfmesh-balance stop
/etc/init.d/obfmesh-balance disable
```

`obfmesh-balance status` на этом месте отвечает только за половину вопроса: про таблицу он скажет
(строка `nft table` — «есть» или «НЕТ»), а в строке `ip rule` печатает формулу приоритетов из
конфигурации, а не то, что стоит в ядре. Что осталось в ядре, показывает `ip rule show`, и ничто
другое.

Сразу, когда след надо убрать немедленно и ждать нечего:

```sh
obfmesh-balance off                            # чтобы демон не собрал ruleset заново
obfmesh-balance teardown                       # таблица, правила 31000+i и страховки 31500+i
/etc/init.d/obfmesh-balance stop
/etc/init.d/obfmesh-balance disable
ip rule show | grep -E '^31[05][0-9][0-9]:' || echo 'правил и страховок нет'
nft list table inet obfmesh_balance 2>/dev/null || echo 'таблицы нет'
```

Порядок `off` → `stop` без ожидания и без `teardown` оставляет в ядре таблицу, правила и
страховки: `stop` мягкий, а снимать их станет уже некому.

Дальше, если нужно вернуть жёсткую раскладку из 3.7, — вернуть секциям прежнюю привязку по снимку
`/root/forkop.before-balance` и перезапустить Forkop. Возвращается та форма, что была в снимке:
`outbound_json` целиком, если `bind_interface` стоял внутри него, и отдельная опция секции, если
она была отдельной. Порядок именно такой: сначала снять балансировку, потом менять привязки.

Снять пакет целиком:

```sh
apk del obfmesh-balance
```

Свой след из ядра убирает `prerm`: он зовёт `obfmesh-balance teardown`, то есть жёсткое снятие со
всеми его последствиями для переброшенных соединений. Не `stop` — остановка сервиса мягкая и
таблицу с правилами оставляет. Рабочий каталог `/var/run/obfmesh-balance` уносит `postrm`. При
**обновлении** пакета (`PKG_UPGRADE=1`) оба шага пропускаются: таблица, правила и страховки
остаются на месте, новый демон пересоберёт своё на ближайшем такте. Секции Forkop остаются на
адресе базового луча — их возвращает только человек.

## 4. Число обфускаторов

### 4.1 Сколько лучей

Число лучей — одна настройка на сервере, всё остальное подтягивается само: сервер поднимает
недостающие `swg{i}` и обфускаторы, повышает `config_version`, роутер получает событие по SSE,
скачивает новый бандл и меняет только разницу. Диапазон 1..10.

С роутера (нужен админ-ключ в uci):

```sh
uci set obfmesh.main.api_key='<админ-ключ сервера>'
uci commit obfmesh
obfmesh spokes            # прочитать
obfmesh spokes 3          # изменить
obfmesh status
```

С сервера:

```sh
KEY=$(sudo cat /etc/obfmesh/admin.key)
curl -s -X PATCH http://127.0.0.1:8080/api/settings \
     -H "X-API-Key: $KEY" -H 'Content-Type: application/json' \
     -d '{"spokes":3}'
```

Или в панели, раздел «Настройки лучей».

Уменьшение гасит только лишние лучи вместе с их таблицами и правилами: работающие не трогаются, их
ключи остаются в базе, поэтому обратное увеличение не меняет уже выданные бандлы. Установленные
сессии на оставшихся лучах не рвутся — маршруты этих лучей не меняются вообще.

**Сколько ставить.** На NanoPi R3S проверено замерами: два луча — 359–373 Мбит/с, три —
210–222 Мбит/с. Третий луч отнимает скорость, потому что процессор роутера уже загружен на
92–98 %. Увеличивать число лучей имеет смысл только на более сильном клиенте и только с замером до
и после.

### 4.2 Как убедиться, что луч действительно работает

«Интерфейс поднят» и «трафик идёт» — разные вещи. Каждый луч проверяется отдельно и полностью.

На роутере, для луча i (пример для первого):

```sh
ip -4 addr show owg1                   # 10.77.1.2/30, и этого адреса нет больше нигде
ip route show table 51821              # ровно одна строка: default dev owg1 mtu 1400
ip rule show | grep 51821              # 32001: from 10.77.1.2 lookup 51821
ping -c3 -I owg1 10.77.1.1
curl --interface owg1 -s https://ifconfig.me; echo
wg show owg1 transfer                  # оба счётчика растут
```

На сервере:

```sh
wg show swg1 allowed-ips               # 10.77.1.2/32 — один адрес, и только он
wg show swg2 allowed-ips               # 10.77.2.2/32
ip route show | grep 10.77.            # только подсети swg{i}, без nexthop-конструкций
```

Ключевой момент: адрес клиента принадлежит ровно одному лучу с обеих сторон. Второй адрес в
AllowedIPs, многопутевой маршрут к клиенту, устройство `agg0`, непустая таблица `51820` — это следы
схемы 1.1.0, а не рабочая конфигурация. После обновления с 1.1.0 стоит убедиться, что их не
осталось:

```sh
ip link show agg0 2>/dev/null && echo 'ОСТАТОК 1.1.0: agg0'
ip route show table 51820 | grep . && echo 'ОСТАТОК 1.1.0: таблица 51820'
ip rule show | grep -E '^30000:' && echo 'ОСТАТОК 1.1.0: правило oif agg0'
ip -4 addr show | grep '10\.77\.0\.' && echo 'ОСТАТОК 1.1.0: агрегатный адрес'
```

**Реактивность.** На роутере:

```sh
obfmesh status | grep watcher          # running
logread -e obfmesh | tail -20          # ошибок чтения bundle.json быть не должно
```

Меняем число лучей на сервере (4.1) и через десяток секунд смотрим на роутере:

```sh
obfmesh status                         # config_version вырос сам, без ручного obfmesh sync
```

Если новое значение появляется только после ручного `obfmesh sync` — watcher до сервера не
доходит: смотрите `logread -e obfmesh` сразу после старта сервиса.

## 5. Диагностика

### 5.1 Куда смотреть

| Где | Команда или файл | Что там |
|---|---|---|
| сервер | `journalctl -u obfmesh-server -n 80` | API, reconcile, ошибки оркестратора |
| сервер | `/var/log/obfmesh/obf{i}.log` | вывод серверного обфускатора луча i |
| сервер | `obfmesh-ctl status` | лучи, интерфейсы, живость обфускаторов без HTTP |
| сервер | `obfmesh-ctl reconcile` | привести систему к состоянию из базы и показать, что менялось |
| роутер | `obfmesh status`, `obfmesh status --json` | сводка |
| роутер | `obfmesh logs -n 100`, `logread -e obfmesh` | apply.sh и watcher |
| роутер | `/var/run/obfmesh/obf-c{i}.log` | вывод клиентского обфускатора луча i |
| роутер | `/var/run/obfmesh/state.json` | что реально применено |
| роутер | `ip route show table 51820+i`, `ip rule show` | маршруты лучей |
| роутер | `obfmesh-balance status`, `obfmesh-balance check` | балансировка: веса, карта в ядре, привязки Forkop |
| роутер | `obfmesh-balance logs -n 100`, `logread -e obfmesh-balance` | демон весов и транзакции nft |
| роутер | `nft list table inet obfmesh_balance` | карта весов и цепочки балансировщика |

Секреты в логи и в вывод команд не попадают: на их месте `<есть>`.

### 5.2 Симптом → куда смотреть

| Симптом | Что проверить |
|---|---|
| `obfmesh status` пуст, бандла нет | `obfmesh logs -n 50`; `server_url`, `token`, `ca_file`; `curl` из шага 3.3 |
| `GET /api/bundle` отвечает 401 | токен не тот или клиент удалён; заведите клиента заново |
| `GET /api/bundle` отвечает 409 | на сервере ещё нет лучей или не задан `external_host`: `obfmesh-ctl reconcile` |
| Луч поднят, рукопожатия нет | путь до `48200+i`: `tcpdump -ni any udp port 48201` на сервере; INPUT-правила |
| Обфускатор `DEAD` на роутере | `cat /var/run/obfmesh/obf-c1.log`; частая причина — занятый порт `13301` |
| Обфускатор падает на сервере | `tail -50 /var/log/obfmesh/obf1.log`, `journalctl -u obfmesh-server -n 80` |
| Рукопожатия идут, трафика нет | маскировка: `grep masking /etc/obfmesh/obf1.conf` и `/var/run/obfmesh/obf-c1.conf` — значения должны совпадать байт в байт |
| Через `owg{i}` не ходит ничего | проверка из 4.2 целиком: адрес, таблица, правило, AllowedIPs на сервере |
| Скорость как у одного луча | все потребители сидят на одном интерфейсе: `wg show owg2 transfer` не растёт — раскладка из 3.7 |
| Скорость около 210 вместо 359 Мбит/с | настройка роутера не применилась: проверка из 3.6 (`taskset`, `rps_cpus`, `netdev_budget`) |
| Скорость упала после добавления третьего луча | так и должно быть на R3S: 210–222 против 359–373, см. 4.1 |
| Один поток не разгоняется выше ~180 Мбит/с | это потолок одной TCP-сессии, лечения нет (SPEC, «Что проверено и отвергнуто») |
| Ответы не приходят на тот луч, с которого ушли | `wg show swg{i} allowed-ips` — там должен быть ровно один адрес клиента |
| Часть секций потребителя потеряла интернет | их луч погашен уменьшением `spokes`; перевесить `bind_interface` на живой |
| Изменения на сервере не подхватываются | строка `watcher` в `obfmesh status`; `logread -e obfmesh` |
| Сервис «останавливается» и встаёт обратно | `ls /var/run/obfmesh/admin-down` — watcher уважает этот маркер |
| После `systemctl stop` на сервере туннели живы | так задумано: `KillMode=process`. Гасить — `obfmesh-ctl teardown` |
| Панель отдаёт 502/504 на `/api/events` | буферизация прокси: `flush_interval -1` у Caddy, `proxy_buffering off` у nginx |
| После обновления пропал токен | конфиг перезаписан мимо пакетного менеджера; `/etc/config/obfmesh` обязан быть в `conffiles`, см. PACKAGING.md, 2.5 |
| Балансировщик включён, а трафик весь в базовом луче | `obfmesh-balance check`: секция на `bind_interface` или `routing_mark` в цепочку не попадает; `mark_base` должен совпасть с `route.default_mark` |
| `obfmesh-balance status`: `KERNEL` пуст или расходится с `WEIGHT` | демон не работает или транзакция nft не прошла: `obfmesh-balance logs -n 50` |
| Переброшенное соединение не отвечает | нет SNAT или нет правила `31000+i`: `nft list table inet obfmesh_balance`, `ip rule show \| grep 3100` |
| Правила `31000+i` пропадают после каждого `obfmesh apply` | на роутере obfmesh старше 1.3.0: `obfmesh version`. Начиная с 1.3.0 чужие правила в своих таблицах он не трогает (приложение В) |
| Правила `31000+i` пропадают сами по себе | их снял кто-то ещё; демон вернёт их на следующем такте — `obfmesh-balance logs -n 50` покажет, ставил ли он их заново |
| Часть соединений вдруг никуда не идёт, а базовый луч работает | сработала страховка `31500+i`: таблица луча пуста, и помеченный пакет отбрасывается вместо утечки в WAN. Проверить `ip route show table 51820+i` и `obfmesh status` — луч погашен или obfmesh остановлен |
| После `obfmesh-balance teardown` соединения не рвутся, а висят | так и работает: conntrack пережил снятие таблицы, `nf_nat` доигрывает старый SNAT, пакет уходит в базовый луч с чужим адресом источника и дропается пиром. Ждать таймаута приложения или переоткрыть соединение |
| Пакет выключили, а таблица и правила на месте | это мягкая остановка, и она штатная. Работающий демон снимет их через `OMB_SOFT_GRACE` (600 с); демона нет — снимать некому, `obfmesh-balance teardown` |

### 5.3 Ручные операции на роутере

```sh
obfmesh sync                # забрать бандл и применить, если изменился
obfmesh apply               # применить сохранённый бандл (снимает administrative down)
obfmesh down                # погасить всё, оставив сервис включённым
obfmesh logs -f             # хвост лога
obfmesh version             # версии пакета, бандла, обфускатора
```

`obfmesh down` ставит маркер `/var/run/obfmesh/admin-down`, иначе watcher поднял бы всё обратно на
ближайшем тике. Маркер живёт в tmpfs: после перезагрузки роутера туннель поднимется снова.

Балансировщик, если он установлен:

```sh
obfmesh-balance status          # веса, живость лучей, что лежит в карте nft
obfmesh-balance check           # почему не работает: привязки Forkop, метка, правила
obfmesh-balance apply           # пересобрать ruleset и правила прямо сейчас
obfmesh-balance weights 1:70 2:30   # ручные веса, переводит mode в manual
obfmesh-balance off              # мягко: новые соединения базовым лучом, Forkop не трогается.
                                 # Таблица, правила 31000+i и страховки 31500+i ОСТАЮТСЯ — по ним
                                 # доживают переброшенные соединения; работающий демон снимет их
                                 # через OMB_SOFT_GRACE (600 с)
obfmesh-balance teardown         # жёстко и сразу: снять таблицу, правила и страховки.
                                 # Переброшенные соединения после этого виснут до таймаута
                                 # приложения — сбросить им conntrack нечем
```

## 6. Удаление начисто

### 6.1 Роутер

```sh
# 1. Вернуть потребителям прежний выходной интерфейс (обратный шаг 3.7).
obfmesh-balance off              # если ставился: сначала enabled = 0, иначе демон успевает
                                 # собрать таблицу и правила заново между teardown из prerm
                                 # и остановкой сервиса
apk del obfmesh-balance          # его prerm зовёт obfmesh-balance teardown,
                                 # то есть снимает таблицу nft, правила 31000+i и страховки 31500+i
/etc/init.d/obfmesh stop
apk del luci-app-obfmesh obfmesh
```

Порядок обязателен: obfmesh-balance читает состав лучей у obfmesh, и снятый раньше времени obfmesh
оставил бы правила `31000+i`, ведущие в пустые таблицы. По той же причине в init-скриптах
балансировщик стартует после (`START=96` против `95`) и останавливается раньше (`STOP=9` против
`10`). Окно между `STOP=9` и `STOP=10` — то, в котором obfmesh уже сделал
`ip route flush table 51820+i`, а помеченные соединения ещё живы, — закрывают страховки
`31500+i`: помеченный пакет там отбрасывается, а не уходит в WAN под MASQUERADE.

`stop` гасит лучи, чистит таблицы `51820+i` и снимает правила. Удаление пакета дополнительно
стирает `/etc/obfmesh/bundle.json` (в нём приватные ключи) и весь `/var/run/obfmesh` (в нём
`curl.rc` с токеном).

Проверка, что не осталось следов:

```sh
ip link show owg1 2>/dev/null || echo 'лучи убраны'
ip route show table 51821                # пусто
ip rule show | grep -E '^320[0-9][0-9]:' || echo 'правил нет'
ip rule show | grep -E '^31[05][0-9][0-9]:' || echo 'правил и страховок балансировщика нет'
nft list table inet obfmesh_balance 2>/dev/null || echo 'таблицы балансировщика нет'
ls /etc/obfmesh /var/run/obfmesh 2>&1    # нет таких каталогов
pgrep -af wg-obfuscator || echo 'обфускаторов нет'
ping -c2 8.8.8.8                         # домашний интернет жив
```

Настройки, которые делал `tune.sh` (governor, RPS, `netdev_budget`), живут до перезагрузки и
никакого следа в конфигурации не оставляют. Нужно вернуть их немедленно — перезагрузите роутер или
верните значения руками.

Пакет `ip-full` ставился отдельно и остаётся: его могли использовать другие сервисы. Убирать —
только сознательно.

### 6.2 Сервер, установка пакетом

```sh
apt-get purge -y obfmesh-server
```

`prerm` останавливает сервис, гасит обфускаторы и удаляет интерфейсы `swg{i}`, `purge` стирает
`/etc/obfmesh` (админ-ключ, конфиги с ключом обфускации), `/var/lib/obfmesh` (база) и
`/var/log/obfmesh`. Без `purge` база и ключи остаются — переустановка их подхватит.

### 6.3 Сервер, установка из исходников

```sh
systemctl disable --now obfmesh-server
obfmesh-ctl teardown --interfaces
rm -rf /opt/obfmesh /etc/obfmesh /var/lib/obfmesh /var/log/obfmesh /run/obfmesh
rm -f /etc/systemd/system/obfmesh-server.service /etc/logrotate.d/obfmesh /usr/local/sbin/obfmesh-ctl
rm -rf /etc/systemd/system/obfmesh-server.service.d
systemctl daemon-reload
```

### 6.4 Общее для обоих способов

Правила NAT и FORWARD общие для всех лучей и ни `purge`, ни `teardown` их не снимают — иначе
удаление одного экземпляра сломало бы соседний. Снимаются вручную:

```sh
iptables -t nat -D POSTROUTING -s 10.77.0.0/16 ! -d 10.77.0.0/16 -j MASQUERADE
iptables -D FORWARD -s 10.77.0.0/16 -j ACCEPT
iptables -D FORWARD -d 10.77.0.0/16 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
for p in $(seq 48201 48210); do iptables -D INPUT -p udp --dport $p -j ACCEPT 2>/dev/null; done
```

Блок обратного прокси из конфигурации Caddy/nginx убирается отдельно, вместе с перезагрузкой
прокси.

| `obfuscator_extra_args` | — | дополнительные аргументы обфускатору |

Опций `agg_iface`, `agg_address`, `route_table`, `rule_pref` и `fwmark` в 1.2.0 нет: единого
агрегирующего устройства и единой таблицы туннеля больше не существует. Если раньше трафик
заворачивался в туннель по метке, теперь метка направляется в конкретный луч своим правилом,
поставленным рядом с obfmesh:

```sh
ip rule add fwmark 0x1 lookup 51821 pref 30001     # метка 0x1 → первый луч
```

**Приоритет выбирается не любой свободный.** Заняты две полосы obfmesh-balance (раздел 3.8):
`31001..31010` — его правила лучей, `31501..31510` — их страховки `blackhole`. Правило соседа с тем
же приоритетом ему мешает. Полоса `32001..32010` — самого obfmesh. Ниже `31000` и выше правила
Forkop `pref 105` места достаточно, поэтому пример и стоит на `30001`.

Такое правило obfmesh не ведёт, не снимает при остановке и не сносит на `apply`: он считает и
чистит только правила своего приоритета `32000+i`, а всё остальное, что смотрит в его таблицы, —
чужая настройка (SPEC.md, инвариант 8). Раньше обещание нарушалось кодом: первый же `apply`
уносил такое правило вместе со своими, и заметить это можно было только по пропавшему трафику.
Исправлено вместе с выпуском obfmesh-balance, который на этом механизме и построен.

Два исключения, оба намеренные.

**Селектор, дословно совпавший со своим.** С 1.3.0 obfmesh узнаёт свои правила по селектору:
`from <адрес луча> lookup <таблица луча>` и `oif <устройство луча> lookup <таблица луча>`. Такую
строку он снимает на **любом** приоритете — иначе смена `rule_pref_base` оставляла бы прежнюю пару
в ядре навсегда. Поэтому заворот в луч ставится по метке, а не повторением адреса луча в `from`:
`ip rule add from 10.77.1.2 lookup 51821 pref 30001` — это дословно правило obfmesh, и оно уйдёт
на ближайшем `apply`. Правило с любым другим селектором (`fwmark`, `iif`, чужой `from`) остаётся
на месте.

**Общая таблица `51820` схемы 1.1.x** чистится целиком, вместе с чужими правилами. Ею эта версия
не пользуется, и любое смотрящее в неё правило ведёт в никуда.

Готовый потребитель механизма — пакет obfmesh-balance (раздел 3.8): он ставит правила
`fwmark 0x{i}00/0xff00 lookup 51820+i` на приоритетах `31000+i`, страховки
`fwmark 0x{i}00/0xff00 blackhole` на `31500+i` и держит живыми и те, и другие.

Своим он считает правило, у которого сошлись оба признака: приоритет ровно `31000+i` и селектор
ровно `fwmark 0x{i}00/0xff00`; страховку — так же строго, приоритет ровно `31500+i` и то же
действие `blackhole`. Правило по метке, поставленное рядом на другом приоритете, под это не
подходит и остаётся (SPEC.md, раздел про инварианты obfmesh-balance).

В таблицу базового луча он правил не ставит — метка базового луча не меняется, уводить нечего. Но
свой след там снимает: луч, который раньше был небазовым, оставляет правило `31000+i`, и при смене
`base_spoke` оно уходит по тем же двум признакам. «Не ставит» и «не чистит» — разные вещи, и
рассчитывать на второе нельзя.

## Приложение Г. Опции uci пакета obfmesh-balance

Секция `config balance 'main'`, файл `/etc/config/obfmesh-balance` (объявлен в `conffiles`).
Секретов в нём нет, но есть настройка живого роутера, поэтому обновление пакета его не
перезаписывает. Демон перечитывает конфигурацию на каждом такте — `reload` нужен только чтобы
поднять его, если он не запущен.

| Опция | По умолчанию | Что делает |
|---|---|---|
| `enabled` | `0` | `0` — пакет не создаёт ни таблицы, ни правил. Включать после `obfmesh-balance check` |
| `base_spoke` | `1` | индекс луча, на адрес которого биндятся секции Forkop, `1..10` — столько лучей вообще бывает. Его трафик не перемаршрутизируется и не SNAT-ится |
| `mode` | `auto` | `auto` — веса считает демон; `manual` — берутся из `weights` и не пересчитываются; `off` — сервис демона не поднимает, а уже работающий переходит в мягкую остановку (карта весов на базовый луч) и через `OMB_SOFT_GRACE` снимает своё целиком |
| `interval` | `5` | период такта, секунды, `1..3600` |
| `min_share` | `10` | минимальная доля живого луча, проценты, `0..100`. Если `min_share × N > 100`, порог урезается до `100/N` |
| `max_step` | `15` | предел изменения веса за такт, процентные пункты, `1..100`. Он же скорость возвращения поднявшегося луча |
| `weights` | — | список ручных весов для `mode = manual`: `list weights '1:60'` (по индексу луча) или `list weights '40'` (позиционно, по возрастанию индекса). Формы смешиваются; сумма приводится к 100. Остаток сначала делится поровну между живыми лучами, которых в списке НЕТ, и только то, что осталось после них, достаётся базовому: при двух лучах `1:60` даёт 60/40, а не 60/0. Явный ноль — не «луч не назван»: `2:0` оставляет лучу 2 ноль. Мёртвый луч получает ноль независимо от списка |
| `rule_pref_base` | `31000` | база приоритетов: правило небазового луча i — `rule_pref_base + i`, его страховка `blackhole` — `rule_pref_base + 500 + i`. Допустимо `200..31489`: ниже 200 правило встало бы впереди правила Forkop `pref 105` и tproxy не увидел бы свой пакет; выше — страховка задела бы полосу obfmesh (`32000+i`). Негодное значение всегда заменяется на 31000, но говорит об этом не всякое: `1..199` и `31490..32700` дают строку `warn` в логе, а не число, ноль и всё, что больше 32700, подменяются молча — их отсекает общая проверка числа до разбора границ |
| `mark_base` | `0x08000000` | база меток; обязана совпадать с `route.default_mark` в конфигурации sing-box. Запрещены бит `0x04000000`, любой бит из байта `0x0000FF00`, значение шире 32 бит и ноль (при нулевой базе цепочка `out` поймала бы весь НЕпомеченный трафик с адреса базового луча). Такое значение отвергается со строкой в логе, берётся `0x08000000` |
| `table_name` | `obfmesh_balance` | имя своей таблицы nft. Имя, где есть что-то кроме букв, цифр и подчёркивания, отвергается целиком — берётся `obfmesh_balance` |

Диапазоны у `base_spoke`, `interval`, `min_share` и `max_step` проверяются одинаково и **молча**:
пустая строка, минус, `abc`, `5s`, `0x10` и любое число за границей диапазона дают значение по
умолчанию из этой же таблицы, и ни строки в лог при этом не пишется. Опечатку в них видно только по
`obfmesh-balance status`: он печатает то, что реально прочитано, — строками `base spoke : 1` и
`mode : auto (interval 5s, min_share 10%, max_step 15)`. Проверять — там, а не в `uci show`.

Настройками не являются и в uci не выносились (все они — константы `lib.sh`):

| Константа | Значение | Что решает |
|---|---|---|
| `OMB_HS_MAX` | `180` | сколько секунд по монотонным часам сырое `latest-handshakes` может стоять на месте, прежде чем луч объявлен мёртвым |
| `OMB_MUTE_TICKS` | `3` | сколько тактов подряд `tx` растёт при стоящем `rx`, чтобы вывести односторонний луч, не дожидаясь протухшего рукопожатия |
| `OMB_MUTE_SECS` | `30` | и сколько при этом секунд: `interval` настраивается, а `persistent-keepalive` на лучах 25 секунд |
| `OMB_REDISCOVER` | `300` | период полного перечитывания состава лучей у obfmesh; между ними состав перечитывается по смене набора адресов на `owg*` |
| `OMB_SOFT_GRACE` | `600` | сколько выключенный пакет держит мягкую остановку, прежде чем работающий демон снимет таблицу, правила и страховки. Отсчёт идёт только в цикле демона и только при `enabled = 0` или `mode = off`; демона нет — мягкое состояние держится до перезагрузки или до `obfmesh-balance teardown`. Читается из окружения, чтобы тестам не ждать десять минут |

Приоритеты страховок отдельной опцией тоже не задаются: смещение `+500` от `rule_pref_base`
зашито (`OMB_RULE_GUARD_OFF`), и верхняя граница `rule_pref_base` посчитана именно по ним.

Рабочий каталог — `/var/run/obfmesh-balance` (700): `state.json` — что применено последним тактом,
`ruleset.md5`, `weights.sig` и `skeleton.sig` — подписи, по которым демон решает, надо ли вообще
трогать nft, `daemon.pid`.
