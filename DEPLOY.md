# Выкат obfmesh на боевые машины

Цели: сервер `45.136.127.10` (Ubuntu 24.04, Python 3.12, 4 ядра) и роутер `192.168.2.1`
(FriendlyWrt 25.12.5, NanoPi R3S, aarch64, BusyBox ash, apk, procd).

На роутере работает Forkop и раздаёт интернет домой. Ни один шаг ниже не трогает главную таблицу
маршрутизации, firewall роутера и конфигурацию Forkop: obfmesh создаёт свои интерфейсы `owg{i}`,
свои таблицы `51820+i` и свои правила `32000+i`. Пока секции Forkop не привязаны к лучам, выкат для
домашней сети незаметен, а любой шаг откатывается одной командой.

Порядок: сначала сервер целиком, потом роутер. Обратный порядок бессмыслен — клиенту неоткуда
взять бандл.

Обозначения: `[S]` выполняется на сервере под root, `[R]` — на роутере под root.

Версия 1.2.0 меняет схему: `agg0`, VRF, `teql` и агрегатный адрес удалены, лучи независимы. Если
на машинах стоит 1.1.0, шаги 6 и 7 выполняются как обновление — с проверкой, что от старой схемы
ничего не осталось.

## Шаг 0. Подготовка, ничего не меняет

`[S]`

```sh
ssh root@45.136.127.10
uname -a; python3 -V; systemctl --version | head -1
command -v wg ip iptables || echo 'ЧЕГО-ТО НЕТ'
ss -lntp | grep -E ':(443|8080)\b' || echo 'порты 443 и 8080 свободны'
```

`[R]`

```sh
ssh root@192.168.2.1
cat /etc/openwrt_release | head -3; uname -r; nproc
apk info -e ip-full wireguard-tools curl jsonfilter
ls -l /usr/bin/wg-obfuscator
ip route show table 51821; ip route show table 51822    # должны быть пустыми
ip rule show | grep -E '^320[0-9][0-9]:' || echo 'приоритеты свободны'
```

**Проверка.** `wg`, `ip`, `iptables` есть на сервере; на роутере известно, каких пакетов не
хватает, таблицы `51821+` и приоритеты `32001+` свободны.

**Откат.** Не требуется.

Если таблицы или приоритеты заняты чужим сервисом, на шаге 7 задаются другие базы:
`uci set obfmesh.main.route_table_base=...`, `uci set obfmesh.main.rule_pref_base=...`.

## Шаг 1. Бинарник обфускатора на сервере

`[S]`

```sh
install -m 0755 wg-obfuscator /usr/local/bin/wg-obfuscator
/usr/local/bin/wg-obfuscator --help | grep -i masking
/usr/local/bin/wg-obfuscator --version
```

**Проверка.** В выводе `--help` есть `masking`, среди значений — `STUN`. Без этого obfmesh
откажется поднимать луч: без маскировки провайдер режет поток, а выглядит это как «туннель
поднят, трафика нет».

**Откат.** `rm -f /usr/local/bin/wg-obfuscator`.

## Шаг 2. Установка управляющего сервиса

`[S]`

```sh
apt-get install -y wireguard-tools iproute2 iptables python3-venv
cd /root/obfmesh/server
OBFMESH_EXTERNAL_HOST=45.136.127.10 \
OBFMESH_OBFUSCATOR_BIN=/usr/local/bin/wg-obfuscator \
./install.sh
```

**Проверка.** Скрипт должен закончиться строкой про поднятые лучи:

```sh
systemctl is-active obfmesh-server
obfmesh-ctl status
wg show swg1 | head -5
wg show swg1 allowed-ips          # у пира клиента ровно один /32
ss -lunp | grep -E ':(48201|48202)\b'
pgrep -af wg-obfuscator
```

Ожидается: сервис `active`, два луча (значение по умолчанию), у каждого поднят интерфейс и жив
обфускатор, порты `48201` и `48202` слушаются.

**При обновлении, а не первой установке, лучей останется столько, сколько было.** Значение по
умолчанию 2 действует только для новой базы: миграция чужую настройку не переписывает — это
осознанно, менять число лучей за спиной оператора она не должна. Если на 1.1.0 стояло три,
их и будет три, и суммарная скорость будет 210–222 Мбит/с вместо 359–373. Проверить и поправить:

```sh
obfmesh-ctl status | grep -i spokes
curl -s -H "X-API-Key: <админ-ключ>" http://127.0.0.1:8080/api/settings | grep -o '"spokes":[0-9]*'
```

Менять — с роутера, `obfmesh spokes 2` (шаг 8), либо `PATCH /api/settings` здесь же.

Если что-то не так: `journalctl -u obfmesh-server -n 80`, `tail -50 /var/log/obfmesh/obf1.log`.

**Откат.**

```sh
systemctl disable --now obfmesh-server
obfmesh-ctl teardown --interfaces
rm -rf /opt/obfmesh /etc/obfmesh /var/lib/obfmesh /var/log/obfmesh /run/obfmesh
rm -f /etc/systemd/system/obfmesh-server.service /etc/logrotate.d/obfmesh /usr/local/sbin/obfmesh-ctl
systemctl daemon-reload
```

## Шаг 3. Публикация API наружу

Сервис слушает только 127.0.0.1:8080. Без обратного прокси роутер до него не достучится.

`[S]`, вариант с Caddy:

```sh
apt-get install -y caddy
cat /etc/obfmesh/caddy-snippet.txt          # готовый блок
```

Добавить блок в site-блок `/etc/caddy/Caddyfile`. Для голого IP минимальный файл:

```
45.136.127.10 {
    handle_path /obfmesh/* {
        reverse_proxy 127.0.0.1:8080 {
            flush_interval -1
        }
    }
}
```

```sh
caddy validate --config /etc/caddy/Caddyfile
systemctl reload caddy
```

**Проверка.**

```sh
curl -sk -o /dev/null -w '%{http_code}\n' https://45.136.127.10/obfmesh/api/status
# ожидается 401 — прокси работает, аутентификация на месте

KEY=$(cat /etc/obfmesh/admin.key)
curl -sk -H "X-API-Key: $KEY" https://45.136.127.10/obfmesh/api/status | head -c 200
```

Для голого IP Caddy выписывает сертификат своим внутренним CA. Забираем корневой сертификат — он
понадобится роутеру:

```sh
cp /var/lib/caddy/.local/share/caddy/pki/authorities/local/root.crt /root/obfmesh-ca.crt
```

**Откат.** Убрать блок из Caddyfile, `systemctl reload caddy`. На obfmesh это не влияет.

## Шаг 4. Клиент и токен

`[S]`

```sh
KEY=$(cat /etc/obfmesh/admin.key)
curl -s -X POST http://127.0.0.1:8080/api/clients \
     -H "X-API-Key: $KEY" -H 'Content-Type: application/json' \
     -d '{"name":"nanopi"}'
```

Токен в ответе показывается **один раз**. Потеряли — `POST /api/clients` заново под другим именем
либо новый токен тем же способом, каким заводится клиент.

**Проверка.**

```sh
curl -s -H "X-API-Key: $KEY" http://127.0.0.1:8080/api/clients
wg show swg1 allowed-ips        # 10.77.1.2/32, ровно один адрес
wg show swg2 allowed-ips        # 10.77.2.2/32
```

Второй адрес у пира — след схемы 1.1.0 с агрегатным адресом; на 1.2.0 его быть не должно.

**Откат.** `curl -s -X DELETE -H "X-API-Key: $KEY" http://127.0.0.1:8080/api/clients/nanopi`

## Шаг 5. Проверка портов снаружи

Без этого шага дальше идти нет смысла: клиент не достучится до `48201+`.

С любой третьей машины:

```sh
nc -u -z -w3 45.136.127.10 48201; echo $?
```

`[S]` — параллельно смотрим, дошло ли:

```sh
tcpdump -ni any udp port 48201 -c 5
```

**Проверка.** Пакеты видны в tcpdump. Если нет — смотрите правила: сервис по умолчанию сам
вставляет ACCEPT в INPUT (`OBFMESH_MANAGE_INPUT=1`), но внешний firewall провайдера или ufw может
резать раньше.

```sh
iptables -S INPUT | grep 4820
```

**Откат.** Не требуется.

## Шаг 6. Пакеты на роутер

Связь домашней сети на этом шаге не затрагивается. Единственная опасность — `ip-full` вытесняет
`ip-tiny`; ставим одной командой, чтобы роутер не остался без `ip`.

`[R]`

```sh
cp /etc/config/network /etc/config/network.pre-obfmesh
cp /etc/config/firewall /etc/config/firewall.pre-obfmesh
cp /etc/config/obfmesh /root/obfmesh.uci.pre-1.2.0 2>/dev/null   # только при обновлении

apk add ip-full
ip -V && ip rule show | head -3        # ip на месте и умеет rule
```

**Ставится установщиком, а не пакетом.** Собранного `.apk` в репозитории нет и взять его негде:
пакет собирается SDK OpenWrt, а это Linux x86_64 (PACKAGING.md, 2.1) — на машине, с которой идёт
выкат, его нет. Единственный проверенный путь — `openwrt/obfmesh/install-nosdk.sh`. Он кладёт ровно
те же файлы, что положил бы пакет, не трогает существующий `/etc/config/obfmesh` (в нём токен),
останавливает сервис на время замены и поднимает обратно.

С рабочей машины — исходники на роутер, дальше всё делается на роутере:

```sh
scp -r openwrt/obfmesh root@192.168.2.1:/root/       # каталог целиком: установщику нужен files/
```

`[R]`

```sh
sh /root/obfmesh/install-nosdk.sh
install -m 0755 wg-obfuscator /usr/bin/wg-obfuscator
/usr/bin/wg-obfuscator --help | grep -i masking
```

**Следствие: этих файлов нет в базе apk.** `apk info -e obfmesh` на таком роутере молчит — так и
должно быть, а не «пакет потерялся». Отсюда три вещи, о которых спросят позже:

- обновление — повторный запуск того же установщика с новыми исходниками, `apk upgrade` про него
  не знает;
- `apk del obfmesh` ничего не удалит: снимать придётся файлами, список — в «Полном откате»;
- проверки из PACKAGING.md через `apk info -L/-R` и `apk manifest` к такой установке не применимы,
  вместо них — `ls -l` из блока «Проверка» ниже.

Страница LuCI (`luci-app-obfmesh`) приезжает только пакетом: установщик её не кладёт, и без сборки
её на роутере не будет. На работу obfmesh это не влияет — всё, что умеет страница, умеет CLI.

Пакет `obfmesh-balance` здесь не ставится. Он необязательный, ему нужны уже поднятые лучи и
секции Forkop, переведённые на адрес базового луча, поэтому у него свой шаг 10.

При обновлении с 1.1.0: установщик существующий `/etc/config/obfmesh` не перезаписывает, поэтому
токен и `server_url` остаются на месте, а образца конфига рядом он не кладёт (`.apk-new` бывает
только у установки пакетом). Ручной костыль `/usr/lib/obfmesh/tune.sh` заменяется файлом из
поставки — уберите его вызов из `rc.local`/cron, чтобы настройка не применялась дважды из двух мест.

**Проверка.**

```sh
ls -l /usr/lib/obfmesh/ /usr/bin/obfmesh     # apply.sh, watcher.sh, tune.sh, lib.sh
obfmesh version                               # 1.3.0
grep -c token /etc/config/obfmesh             # токен пережил обновление
ls -l /etc/config/obfmesh                     # 600, файл ваш, а не из поставки
ping -c2 8.8.8.8                              # интернет через Forkop жив
```

**Откат.** `apk del` здесь бесполезен — пакета в базе нет. Файлы снимаются руками:

```sh
/etc/init.d/obfmesh stop; /etc/init.d/obfmesh disable
rm -f /etc/init.d/obfmesh /usr/bin/obfmesh
rm -rf /usr/lib/obfmesh
# /etc/config/obfmesh и /etc/obfmesh (там токен и bundle.json) — отдельным решением,
# при откате «на время» их оставляют
apk add ip-tiny        # если нужно вернуть стоковый пакет; ip-full ставился именно пакетом
```

Обратно на 1.1.0 — запуском установщика из прежних исходников и восстановлением конфига из
`/root/obfmesh.uci.pre-1.2.0`. Схемы несовместимы: сервер 1.2.0 не отдаёт полей `agg_mode` и
`agg_address`, без которых клиент 1.1.0 отвергает бандл целиком, поэтому откат клиента имеет смысл
только вместе с откатом сервера.

## Шаг 7. Настройка и первый запуск на роутере

`[R]`

```sh
scp root@45.136.127.10:/root/obfmesh-ca.crt /etc/obfmesh/server-ca.crt
chmod 600 /etc/obfmesh/server-ca.crt

uci set obfmesh.main.server_url='https://45.136.127.10/obfmesh'
uci set obfmesh.main.token='<токен из шага 4>'
uci set obfmesh.main.obfuscator_bin='/usr/bin/wg-obfuscator'
uci set obfmesh.main.ca_file='/etc/obfmesh/server-ca.crt'
uci commit obfmesh
```

Сначала проверяем доступность сервера, не запуская сервис:

```sh
curl --cacert /etc/obfmesh/server-ca.crt -s -o /dev/null -w '%{http_code}\n' \
     https://45.136.127.10/obfmesh/api/status
# 401 — сервер виден и сертификат принят
```

Если сертификат не принимается, временно `uci set obfmesh.main.tls_insecure=1` — но это открывает
канал управления для перехвата, так что это способ диагностики, а не рабочая настройка.

Запуск:

```sh
/etc/init.d/obfmesh enable
/etc/init.d/obfmesh start
sleep 15
obfmesh status
```

**Проверка.** В `obfmesh status`:

- `config_version` не пустой, применён секунды назад;
- по каждому лучу `LINK up`, `OBFUSC ok:<pid>`, `HANDSHAKE` меньше двух минут;
- у каждого луча свой адрес `10.77.{i}.2/30` и своя таблица `51820+i`;
- `watcher: running`, строки `FAILED` нет.

Дальше — что трафик действительно ходит, по каждому лучу отдельно и не трогая домашнюю сеть:

```sh
ping -c3 -I owg1 10.77.1.1
ping -c3 -I owg2 10.77.2.1
curl --interface owg1 -s https://ifconfig.me; echo      # должен ответить 45.136.127.10
curl --interface owg2 -s https://ifconfig.me; echo
wg show owg1 transfer; wg show owg2 transfer
ip route show table 51821                                # default dev owg1 mtu 1400
ip rule show | grep 5182
```

При обновлении с 1.1.0 — что от старой схемы ничего не осталось:

```sh
ip link show agg0 2>/dev/null && echo 'ОСТАТОК: agg0'
ip route show table 51820 | grep . && echo 'ОСТАТОК: таблица 51820'
ip rule show | grep -E '^30000:' && echo 'ОСТАТОК: правило oif agg0'
ip -4 addr show | grep '10\.77\.0\.' && echo 'ОСТАТОК: агрегатный адрес'
```

**Откат.**

```sh
/etc/init.d/obfmesh stop
/etc/init.d/obfmesh disable
```

Домашний интернет всё это время идёт мимо obfmesh, поэтому откат ничего не рвёт.

## Шаг 8. Настройка роутера и замер

Настройка приезжает с пакетом (`/usr/lib/obfmesh/tune.sh`) и применяется при старте и после
каждого `apply`. Без неё два луча дают 210 Мбит/с вместо 359–373, поэтому замер без проверки
настройки бессмыслен.

`[R]`

```sh
taskset -p "$(cat /var/run/obfmesh/obf-c1.pid)"    # current affinity mask: 4  (CPU2)
taskset -p "$(cat /var/run/obfmesh/obf-c2.pid)"    # current affinity mask: 8  (CPU3)
cat /sys/class/net/eth0/queues/rx-0/rps_cpus       # f
sysctl net.core.netdev_budget                      # 600
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor   # performance
```

Замер одного луча (ожидается около 22 МБ/с ≈ 180 Мбит/с):

```sh
curl --interface owg1 -o /dev/null -s -w 'owg1 %{speed_download} B/s\n' \
     https://speed.hetzner.de/100MB.bin
```

Замер суммы — два потока одновременно, каждый в своём луче (ожидается 359–373 Мбит/с):

```sh
curl --interface owg1 -o /dev/null -s -w 'owg1 %{speed_download} B/s\n' \
     https://speed.hetzner.de/100MB.bin &
curl --interface owg2 -o /dev/null -s -w 'owg2 %{speed_download} B/s\n' \
     https://speed.hetzner.de/100MB.bin &
wait
```

Одним потоком суммы не получить: 180 Мбит/с — потолок одной TCP-сессии, распараллелить её нельзя
(SPEC, «Что проверено и отвергнуто»).

Число лучей меняется на сервере, читается и меняется с роутера:

```sh
uci set obfmesh.main.api_key='<админ-ключ сервера>'
uci commit obfmesh
obfmesh spokes            # прочитать
obfmesh spokes 2          # рабочее значение
```

**Проверка.** `obfmesh status` показывает два луча со свежими рукопожатиями, сумма двух
одновременных замеров — 359–373 Мбит/с.

Третий луч на этой машине проверен и **медленнее**: 210–222 Мбит/с при загрузке процессора
92–98 %. Если всё же меряете — меряйте до и после, а не «на глаз».

**Откат.** `obfmesh spokes 2`. Настройку роутера снимает `uci set obfmesh.main.tune=0` плюс
перезапуск сервиса; прежние значения governor и RPS возвращает перезагрузка.

## Шаг 9. Разведение секций Forkop по лучам

Первый шаг, который реально влияет на домашнюю сеть. Делайте, когда шаг 7 стабильно отработал
хотя бы сутки. Именно здесь получается агрегация: разные сервисы уходят в разные лучи.

`[R]` — до переключения снимите точку отката. Точка отката — **копия файла**
`/etc/config/forkop`, а не вывод `uci show`: вернуть конфигурацию можно только тем, что кладётся
обратно на своё место как есть.

```sh
SNAP=/root/forkop.bak.$(date +%Y%m%d-%H%M%S)
( umask 077; cp /etc/config/forkop "$SNAP" )
chmod 600 "$SNAP"
ls -l "$SNAP"                              # -rw-------
md5sum /etc/config/forkop "$SNAP"          # два хеша обязаны совпасть
grep -nE 'bind_interface|^config ' "$SNAP" # что было привязано и какие секции вообще есть
echo "$SNAP"                               # запишите имя: дальше оно понадобится
```

Рядом — читаемый разбор, он же диагностика. Точкой отката он не является:

```sh
( umask 077; uci show forkop > "$SNAP.uci" )
chmod 600 "$SNAP.uci"
```

`uci show` печатает `forkop.google.outbound_json=...` — плоские строки, удобные для `grep` и
глазами. Обратно в `/etc/config/forkop` их положить нельзя: там нужны `config section`, `option` и
`list`. Форму `list` против `option` по `uci show` тоже не различить, когда в списке один элемент,
а разница потом важна (шаг 10). Всё это видно только в самом файле.

**Снимок снимается непосредственно перед работой.** На этом роутере уже случилось:
`/root/forkop.bak.balance-start` был снят 22.08 в 19:57, конфигурацию правили 23.08 в 00:04, и в
снимке нет целой секции (`kinopub`) — откат таким файлом стёр бы её вместе с её доменами. Перед
восстановлением сверяйте состав: `grep -c '^config ' файл` и список секций из `uci show forkop`.

**Снимок Forkop — файл с секретом.** В `/etc/config/forkop` есть `subscription_urls` секции,
которая работает по подписке, — URL с токеном прямо в пути. Файл остаётся в `/root` на роутере:
не копируется на рабочую машину, не кладётся в `/www` (каталог отдаётся наружу через проброс
11228), не вставляется в переписку. `umask 077` действует только на создание, поэтому права
на уже существующий файл доводит `chmod`.

Дальше — точечно, по одной секции: тяжёлое на один луч, мелкое и разговорчивое на другой. `sed`
в первой команде подменяет значения секретных опций на `<есть>` — тем же маркером obfmesh
показывает наличие секрета в своих отчётах. Без него на экран уедет URL подписки.

```sh
uci show forkop | sed -E "s/^([^=]*(urls?|token|key|secret|password|uuid))=.*/\1='<есть>'/" |
	grep -E 'bind_interface|=.*section'

uci set forkop.<секция_1>.bind_interface='owg1'
uci set forkop.<секция_2>.bind_interface='owg2'
```

**Правки применяет `uci commit forkop`, и он же рвёт соединения.** В `/etc/init.d/forkop` есть
`procd_add_config_trigger`: commit шлёт procd событие `config.change`, procd сам перезапускает
Forkop, тот пересобирает `/etc/sing-box/config.json` и поднимает sing-box заново. Безусловный
`/etc/init.d/forkop restart` следом — это **второй** обрыв всех соединений через прокси, уже ни за
чем. Поэтому: commit, пауза, проверка, и рестарт — только если проверка показала, что триггер не
сработал. Делать в тихое время.

**Смотреть надо на sing-box, а не на Forkop.** У `forkop` нет своего procd-инстанса — он
конфигуратор, а не демон, и `ubus call service list '{"name":"forkop"}'` возвращает пустой объект
и до правки, и после. Процесс, который перезапускается, — это `sing-box`, и Forkop сам дожидается
смены его pid (`wait_sing_box_pid_replacement`, таймаут 15 с). Поэтому наблюдаемых признаков два:
хеш конфигурации и pid sing-box.

```sh
md5sum /etc/sing-box/config.json     # запомнить хеш ДО
pidof sing-box                       # и pid sing-box ДО

uci commit forkop
sleep 10                             # триггер стоит на reload с задержкой 2 с, плюс запас

md5sum /etc/sing-box/config.json     # хеш обязан измениться
pidof sing-box                       # pid обязан стать другим
jsonfilter -i /etc/sing-box/config.json -e '@.outbounds[*].bind_interface'   # ожидается пусто
```

Последняя команда — то же самое, что проверяет сам балансировщик перед включением, поэтому её
результат и его вердикт не разойдутся. Пустой вывод означает, что привязок к устройству
в исходящих не осталось.

Что означает результат:

- хеш другой, pid другой, `bind_interface` пуст — reload уже состоялся, руками ничего не делать;
- хеш прежний либо в `outbounds` осталась старая привязка — триггер не сработал (или собрал
  конфигурацию до правки): только тогда `/etc/init.d/forkop restart` и те же команды ещё раз;
- хеш другой, а pid sing-box прежний — конфигурацию пересобрали, но перечитать её некому: sing-box
  читает её только при старте. Тоже `/etc/init.d/forkop restart`.

**Проверка.**

```sh
curl -s https://ifconfig.me; echo      # с клиента домашней сети — 45.136.127.10
wg show owg1 transfer; wg show owg2 transfer   # растут оба
obfmesh status
```

**Откат.** `uci revert` не поможет — изменения уже зафиксированы `uci commit`. Путей два.

Точечно, когда правились одна-две секции и больше с момента снимка ничего не менялось:

```sh
# привязки не было вовсе — снять опцию
uci delete forkop.<секция_1>.bind_interface
# привязка была другой — вернуть значение из снимка
uci set forkop.<секция_2>.bind_interface='<значение из снимка>'
uci commit forkop                      # и дальше та же проверка триггера, что выше
curl -s https://ifconfig.me; echo      # внешний адрес снова прежний
```

Целиком по снимку, когда правок много или состояние непонятное:

```sh
ls -l /root/forkop.bak.*                                 # выбрать нужный, обычно последний
SNAP=/root/forkop.bak.<дата из имени>

grep -c '^config ' "$SNAP"                               # сколько секций в снимке
uci show forkop | grep -c '=section$'                    # сколько их сейчас — числа должны сойтись
grep -E '^config ' "$SNAP"                               # и глазами: все ли секции на месте

uci revert forkop                                        # сбросить незафиксированные правки:
                                                         # иначе первый же commit затрёт снимок
cat "$SNAP" > /etc/config/forkop                         # права и владелец целевого файла целы
md5sum /etc/config/forkop "$SNAP"                        # хеши совпали — файл лёг целиком
uci -q show forkop >/dev/null && echo 'uci файл читает'
/etc/init.d/forkop restart                               # обязателен: копирование файла
                                                         # procd-события не порождает
```

Числа секций не сошлись — снимок устарел, восстанавливать им нельзя: секции, появившейся после
снимка, вы лишитесь молча. Тогда только точечный путь.

Сеть роутера этот шаг не трогает: правится только конфигурация потребителя. Снимки
`/etc/config/network.pre-obfmesh` и `firewall.pre-obfmesh` из шага 6 лежат на случай, если что-то
правилось руками мимо obfmesh.

Если дальше идёт шаг 10, эта раскладка временная: все секции, привязанные к интерфейсу **базового**
луча, там переезжают на его адрес одним заходом. Оставленная привязка к базовому лучу не даст
включить балансировщик — и это не формальность, а защита от потери трафика такой секции.

## Шаг 10. Балансировка соединений по лучам (пакет obfmesh-balance)

Шаг необязательный. В шаге 9 по лучам разведены сервисы, здесь — отдельные соединения: все
балансируемые секции Forkop выходят с адреса одного луча, а каким лучом пойдёт конкретное
соединение, решает цепочка nft. Делается после того, как шаг 9 отработал хотя бы сутки.
Обоснование, устройство цепочки и полный разбор — INSTALL.md, раздел 3.8; здесь порядок и точки
отката.

Нужен obfmesh **1.3.0 или новее**: до неё первый же `obfmesh apply` сносил правила `31000+i`
балансировщика как чужие в своих таблицах.

`[R]` — проверка перед установкой, ничего не меняет:

```sh
obfmesh version | head -1                      # 1.3.0 или новее, иначе дальше нельзя
uname -r                                       # 6.1.141 — ядро FriendlyElec
ls /lib/modules/$(uname -r)/nft_numgen.ko      # модуль в прошивке; kmod-* на неё не ставят
jsonfilter -i /etc/sing-box/config.json -e '@.route.default_mark'   # 134217728 = 0x08000000
```

Установка — тем же установщиком, что и obfmesh в шаге 6, и по той же причине: собранного `.apk`
нет. Пакет приходит выключенным и в этом состоянии не создаёт ни строки в nft, ни одного `ip rule`.

С рабочей машины:

```sh
scp -r openwrt/obfmesh-balance root@192.168.2.1:/root/     # каталог целиком, вместе с files/
```

`[R]`

```sh
sh /root/obfmesh-balance/install-nosdk.sh
obfmesh-balance version
obfmesh-balance status | grep daemon    # «работает (pid N)» или «не работает» — см. ниже
obfmesh-balance check                   # пакет ещё выключен; смотрим, что помешает включить
```

**Про строку `daemon`.** Установщик останавливает сервис на время замены файлов и в конце пробует
поднять обратно, но `start` при `option enabled 0` штатно ничего не запускает и пишет об этом в
лог. То есть после установки на выключенном пакете демона может не быть, и это нормально: его
поднимет `/etc/init.d/obfmesh-balance start` уже после включения. Верить надо строке `daemon` в
`obfmesh-balance status`, а не тому, что напечатал установщик.

В базе apk этих файлов, как и у obfmesh, нет: `apk info -e obfmesh-balance` молчит, обновление —
повторный запуск установщика, `apk del obfmesh-balance` ничего не удалит и, что важнее, **не
позовёт `prerm`** — таблицу и правила из ядра снимает `obfmesh-balance teardown`, руками
(«Полный откат»).

Секции Forkop переезжают с `bind_interface` на адрес базового луча. **Все, привязанные к лучам, —
и к базовому, и к любому другому, — одним заходом и до включения балансировки.** Дальше луч секции
назначает балансировщик: жёсткая привязка к лучу и балансировка взаимоисключающи, прибитая руками
секция в раскладку не попадает никогда.

Секция на интерфейсе **базового** луча — обязательная и срочная. Адрес источника у неё тот же, что
у переведённой, под фильтр цепочки она попадает, но `SO_BINDTODEVICE` на её сокете переживает
перемаршрутизацию: маршрут в таблице чужого луча не находится, и пакет гибнет в страховке
`31500+i`. Не «не балансируется», а теряет трафик — найдено на пилоте, CHANGELOG.md, запись
obfmesh-balance 1.1.0.

Секция на `bind_interface` **другого** луча под фильтр не попадает и ничего не теряет, но и в
раскладку не идёт: её доля полосы балансировщику не достанется, а нагрузку с её луча регулятор
увидит (прирост он читает у интерфейса целиком) и уведёт оттуда балансируемые соединения. По
замыслу выкатки переводится и она — на боевом R3S это `google` и `wg` на `owg2`. Оставляют такую
привязку только сознательно, ценой того, что сервис навсегда сидит на одном луче.

`routing_mark` не работает вовсе (SPEC.md, «Что проверено и отвергнуто», п. 5). `uci commit forkop`
идёт последним и ровно один раз: он и применяет правки, и рвёт все соединения через прокси —
рестарт Forkop взводит procd-триггер самого commit (шаг 9). Поэтому — в тихое время. Перевод в два
подхода стоит второго такого обрыва, а на половинчатом переводе и замер «до и после» ничего не
показывает: регулятор двигает веса под нагрузку, которую разложить не может.

Состав секций берётся с самого роутера: он живёт в Forkop и меняется без нас, поэтому списка секций
здесь нет. Включённая секция не значит переводимая. На боевом R3S на 22.08.2026 включённых семь, а
`outbound_json` есть у шести: седьмая (`proxysvc`) работает по подписке, узлы ей приходят извне, ни
к какому лучу она не привязана — переводить в ней нечего. Из шести одна (`speedtest`) уже вышла на
адрес базового луча ещё при проверке `routing_mark` — такие пропускаются, переписывать их второй
раз нечего. Цикл, который печатает готовые `uci set` под свой состав и сам пропускает и уже
переведённые секции, и секции без `outbound_json`, — INSTALL.md, 3.8.2.

Точка отката — копия `/etc/config/forkop`, снятая **прямо сейчас**, а не найденная в `/root` от
прошлого раза: на этом роутере уже был случай, когда суточной давности бэкап не содержал целой
секции. Порядок снятия и восстановления — шаг 9, там же про то, чем полезен и чем не является
`uci show forkop`. Файл с секретом: права `600`, живёт только на роутере.

```sh
SNAP=/root/forkop.bak.$(date +%Y%m%d-%H%M%S)
( umask 077; cp /etc/config/forkop "$SNAP" )
chmod 600 "$SNAP"
md5sum /etc/config/forkop "$SNAP"          # хеши совпали — снимок полный
echo "$SNAP"

# в какой форме записан outbound_json: option или list — по uci show этого не видно
grep -nE 'outbound_json|^config ' /etc/config/forkop

# состав: все включённые секции — подлежит ли переводу, имя, исходящий, привязка отдельной опцией
for s in $(uci -q show forkop | sed -n 's/^forkop\.\([A-Za-z0-9_]\{1,\}\)=section$/\1/p'); do
	[ "$(uci -q get "forkop.$s.enabled" 2>/dev/null)" = 0 ] && continue
	oj="$(uci -q get "forkop.$s.outbound_json" 2>/dev/null)"
	bi="$(uci -q get "forkop.$s.bind_interface" 2>/dev/null)"
	case "$oj" in *'}'*'{'*)
		printf 'НЕ ТРОГАТЬ\t%s\tв outbound_json больше одного объекта — разбирать руками\n' "$s"
		continue ;;
	esac
	if [ -n "$oj" ]; then mark='перевод'
	elif [ -n "$bi" ]; then mark='руками'
	else mark='пропуск'
	fi
	printf '%s\t%s\t%s\tbind_interface=%s\n' "$mark" "$s" "$oj" "$bi"
done

# по одной строке на каждую секцию, помеченную «перевод», КРОМЕ тех, где уже стоит
# inet4_bind_address базового луча; тег у секции остаётся прежним
uci set forkop.<секция>.outbound_json='{"type":"direct","tag":"<прежний тег>","inet4_bind_address":"10.77.1.2"}'
uci -q delete forkop.<секция>.bind_interface   # только если привязка стояла отдельной опцией

uci commit forkop      # применяет правки и сам взводит рестарт Forkop; проверка — шаг 9
```

**`НЕ ТРОГАТЬ` — про секцию с несколькими `list outbound_json`.** Такую секцию цикл называет и
пропускает, потому что автоматом её не перевести. `uci -q get` склеивает элементы списка через
пробел, `jsonfilter` на такой строке молча берёт первый объект и возвращает `0`, а `uci set`
схлопывает список в один `option` — второй исходящий исчезает без единого сообщения. Сегодня на
этом роутере у всех секций ровно по одному элементу, и строка не появится; проверка стоит на
завтра. Правится такая секция руками, через `uci delete` списка и `uci add_list` на каждый объект,
со сверкой по снимку.

**Перевод меняет форму записи: `list outbound_json` становится `option outbound_json`.** Это не
поломка — со `speedtest` так уже произошло при проверке `routing_mark`, Forkop такую форму
принимает и секция работает. Знать об этом надо ради отката: в снимке форма прежняя, и возвращать
надо ту, что там записана.

**Безымянные секции цикл не видит.** `sed` в нём отбирает только именованные, а LuCI умеет
создавать секции вида `forkop.@section[0]`. Проверьте, есть ли такие, и разберите их отдельно:

```sh
uci show forkop | grep '=section$' | grep '@' || echo 'безымянных секций нет'
```

Включение делается сразу за перезапуском Forkop: между этими двумя блоками все переведённые секции
идут одним базовым лучом, а это около 111 Мбит/с на всех (замер — в «Проверке» ниже).

```sh
obfmesh-balance check                    # ноль проблем — можно включать
obfmesh-balance on                       # enabled = 1 и сразу применить
/etc/init.d/obfmesh-balance enable
/etc/init.d/obfmesh-balance start        # без демона веса никто не считает
```

**Если перевод не доведён, `on` не включится.** Оставшаяся секция на `bind_interface` интерфейса
базового луча — блокирующая: команда печатает её имя и ту же причину, что и `check`, `enabled`
остаётся `0`, в ядре не появляется ни таблицы, ни правил. Тот же отказ приходит от `apply`, от
`weights` и от каждого такта демона — соседней командой его не обойти. Возврат на предыдущий шаг:
перевести названную секцию (или перевесить её на небазовый луч), `uci commit forkop`,
`/etc/init.d/forkop restart` — и снова `check`.

Опция `uci set obfmesh-balance.main.allow_bind_interface=1` отказ снимает — её печатает сам текст
отказа. На выкате она не ставится: секцию она не чинит, а разрешает балансировщику её ломать, и
доля соединений такой секции продолжает гибнуть в страховке (INSTALL.md, 3.8.2 и 3.8.3).

**Проверка. 1. Что в ядре.**

```sh
obfmesh-balance status                        # WEIGHT и KERNEL совпадают, daemon работает
nft list table inet obfmesh_balance           # карта весов покрывает 0-99 без дыр
ip rule show | grep -E '^310[0-9][0-9]:'      # правило каждого небазового луча
ip rule show | grep -E '^315[0-9][0-9]:'      # и его страховка blackhole
obfmesh-balance logs -n 50
```

Ожидается: таблица есть, у каждого небазового луча ровно два правила — `31000+i` в таблицу луча и
`31500+i` с тем же селектором и действием `blackhole`, — колонки `WEIGHT` и `KERNEL` совпадают.

Растущие счётчики `wg show owgN transfer` сюда не относятся: они растут и без балансировки, если
секции просто разведены по лучам (шаг 9). Ruleset в ядре — тоже ещё не доказательство: он
существует и тогда, когда через него не проходит ни одного пакета.

**Проверка. 2. Что трафик действительно идёт через цепочку.** Пока идёт замер из пункта 3, с
роутера:

```sh
grep -c 'src=10.77.1.2' /proc/net/nf_conntrack     # соединения переведённых секций
grep -c 'mark=134218240' /proc/net/nf_conntrack    # из них уведены на второй луч
```

`134218240` — метка второго луча (`0x08000200`); для луча `i` это `134217728 + 256*i`. Ноль во
второй строке при работающем замере значит, что домен, который вы качаете, не попадает ни в одну
**переведённую** секцию: соединение до цепочки не доходит, и замер меряет что угодно, кроме
балансировки.

**Проверка. 3. Замер: стало ли лучше одному тяжёлому сервису.** Замер делается **с клиента
домашней сети**, а не с роутера. `curl --interface owgN` с роутера кладёт сокет прямо в луч: метки
`0x08000000` на нём нет, а цепочка отбирает по `meta mark 0x08000000 ip saddr 10.77.1.2` — такой
пакет она не видит вовсе. Полный разбор и требования к домену — INSTALL.md, 3.8.4.

Одно TCP-соединение по лучам не раскладывается (потолок одной сессии — около 180 Мбит/с), поэтому
меряются восемь параллельных загрузок одного файла одним сервисом: каждое новое соединение получает
свой бросок `numgen`.

**Домен для замера сначала надо завести в секцию.** `cachefly.cachefly.net` сам по себе не входит
ни в один список Forkop: он получит настоящий адрес, уйдёт напрямую мимо FakeIP, и замер покажет
скорость провайдера, а не балансировки. Проверить — `nslookup cachefly.cachefly.net 127.0.0.42`:
адрес обязан быть из `198.18.0.0/15`. Если это не так, домен добавляется в переводимую секцию
на время замера и убирается после:

```sh
# добавить (на роутере), затем commit и подождать reload, как в шаге 9
cur=$(uci -q get forkop.speedtest.domain)
uci set forkop.speedtest.domain="$cur
cachefly.cachefly.net"
uci commit forkop

# убрать после замера
uci set forkop.speedtest.domain="$cur"
uci commit forkop
```

Каждая такая правка — ещё один reload Forkop и ещё один обрыв соединений, поэтому её делают
вместе с остальными правками секций, а не отдельным заходом.

```sh
# на клиенте домашней сети; домен обязан попадать в переведённую секцию Forkop
URL=https://cachefly.cachefly.net/100mb.test
: > /tmp/omb-speed
for i in 1 2 3 4 5 6 7 8; do
	curl -s -o /dev/null -w '%{speed_download}\n' "$URL" >>/tmp/omb-speed &
done
wait
awk '{ s += $1 } END { printf "итого %.0f Мбит/с\n", s * 8 / 1000000 }' /tmp/omb-speed
```

Прогон А — `obfmesh-balance off`, прогон Б — `obfmesh-balance on`, один за другим, файл и число
потоков те же. Порядок величин на этой машине: **111 Мбит/с** базовым лучом и **359–390 Мбит/с** с
балансировкой. Это ориентир, а не норматив: значение имеет разница А и Б на своей машине, снятая
подряд. С числами шага 8 они не сравниваются — там сокет уходит в луч напрямую с роутера, минуя
sing-box и обфускатор.

`speed.cloudflare.com` для этого замера не годится — с адресов VPS он отвечает 403. `cachefly`
проверен и отдаёт полную полосу.

**Проверка. 4. Регрессия на дефект 1.1.0.** Секция, оставленная на `bind_interface` базового луча,
при включённой балансировке даёт записи conntrack с `packets=0` в обе стороны: соединение ушло на
чужой луч и умерло в страховке. На исправном роутере таких записей нет:

```sh
grep 'mark=134218240' /proc/net/nf_conntrack | grep -c 'packets=0 .*packets=0 '   # ожидается 0
```

Если в `/proc/net/nf_conntrack` вообще нет полей `packets=`, счётчики conntrack выключены и эта
проверка ничего не покажет: `sysctl net.netfilter.nf_conntrack_acct`.

Найденное здесь ненулевое число — это либо секция на `bind_interface` базового луча (`check`
назовёт её), либо снятая руками защита `allow_bind_interface`. С версии 1.1.0 штатным путём в это
состояние не попасть: `obfmesh-balance on` при такой секции просто не включается, `enabled`
остаётся `0`.

**Откат.** Мягко, дав дожить соединениям, уже переброшенным на небазовые лучи:

```sh
obfmesh-balance off                      # новые соединения идут базовым лучом
                                         # демон НЕ останавливать: он снимет остальное сам
sleep 660                                # OMB_SOFT_GRACE 600 с плюс такт демона
ip rule show | grep -E '^31[05][0-9][0-9]:' || echo 'правил и страховок нет'
nft list table inet obfmesh_balance 2>/dev/null || echo 'таблицы нет'
/etc/init.d/obfmesh-balance stop
/etc/init.d/obfmesh-balance disable
```

Немедленно, ценой зависших соединений, — `obfmesh-balance off` и следом `obfmesh-balance teardown`;
почему именно в таком порядке, написано в «Полном откате». Секции Forkop возвращаются к прежней
привязке по снимку `/root/forkop.bak.<дата>` — в той форме, в какой она там записана (`option`
или `list outbound_json`, отдельная опция секции), — отдельным шагом, только после того, как
балансировка снята, и по порядку восстановления из шага 9.

## Полный откат

`[R]`

```sh
# вернуть секциям потребителя прежний интерфейс (шаг 9)

# балансировщик снимается ПЕРВЫМ, если он ставился: состав лучей он читает у obfmesh,
# и снятый раньше времени obfmesh оставил бы его правила смотреть в пустые таблицы
obfmesh-balance off                      # СНАЧАЛА выключить, иначе демон соберёт всё заново
obfmesh-balance teardown                 # таблица nft, правила 31000+i, страховки 31500+i
/etc/init.d/obfmesh-balance stop; /etc/init.d/obfmesh-balance disable
rm -f /etc/init.d/obfmesh-balance /usr/bin/obfmesh-balance /etc/config/obfmesh-balance
rm -rf /usr/lib/obfmesh-balance /var/run/obfmesh-balance

/etc/init.d/obfmesh stop
/etc/init.d/obfmesh disable
rm -f /etc/init.d/obfmesh /usr/bin/obfmesh /etc/config/obfmesh
rm -rf /usr/lib/obfmesh /etc/obfmesh /var/run/obfmesh
ip link show owg1 2>/dev/null || echo 'лучи убраны'
ip route show table 51821                # должно быть пусто
ip rule show | grep -E '^320[0-9][0-9]:' || echo 'правил нет'
ip rule show | grep -E '^31[05][0-9][0-9]:' || echo 'следов балансировщика нет'
nft list table inet obfmesh_balance 2>/dev/null || echo 'таблицы балансировщика нет'
ping -c2 8.8.8.8
```

**Файлами, а не `apk del`.** Пакеты ставились установщиком (шаги 6 и 10) и в базе apk не
зарегистрированы: `apk del obfmesh-balance` скажет, что такого пакета нет, и ничего не сделает —
в том числе не позовёт `prerm`, который снял бы таблицу и правила. Поэтому `teardown` здесь стоит
явно, а файлы перечислены руками. Если пакеты когда-нибудь будут поставлены из `.apk`, `apk del`
сделает то же самое сам, и `rm` станет лишним (проверить: `apk info -e obfmesh obfmesh-balance`).

`off` перед `teardown` — не вежливость, а условие того, что `teardown` вообще подействует. Он
снимает вместе с таблицей и подписи в `/var/run/obfmesh-balance`, а демон при `enabled = 1` видит
на ближайшем такте, что подписи не сходятся, и собирает таблицу и правила заново — то есть через
`interval` секунд (по умолчанию пять) всё возвращается на место. У установки пакетом та же ловушка
ждёт на `apk del`: его `prerm` зовёт `teardown` до того, как apk остановит сервис.

`teardown` здесь не лишний шаг. Остановка сервиса — `/etc/init.d/obfmesh-balance stop` — **мягкая**:
она оставляет таблицу и правила в ядре ради соединений, уже переброшенных на небазовые лучи. Всё
своё снимает только `teardown`, сам по себе или из `prerm`. Эти соединения после него не рвутся, а
виснут до таймаута приложения: запись conntrack переживает снятие таблицы, а сбросить её нечем —
утилиты `conntrack` на роутере нет.

## Что смотреть, когда не работает

| Симптом | Где смотреть |
|---|---|
| `obfmesh status` пуст, бандла нет | `obfmesh logs -n 50`; проверьте `server_url`, `token`, `ca_file` |
| Луч поднят, рукопожатия нет | путь до `48200+i`: `tcpdump -ni any udp port 48201` на сервере |
| Обфускатор `DEAD` на роутере | `cat /var/run/obfmesh/obf-c1.log`; частая причина — занятый порт `13301` |
| Обфускатор падает на сервере | `tail -50 /var/log/obfmesh/obf1.log`, `journalctl -u obfmesh-server -n 80` |
| Рукопожатия идут, трафика нет | маскировка: `grep masking /etc/obfmesh/obf1.conf` и `/var/run/obfmesh/obf-c1.conf` — значение должно совпадать байт в байт (`STUN`) |
| Через `owg{i}` не ходит ничего | `ip route show table 51820+i`, `ip rule show`, `wg show swg{i} allowed-ips` |
| Ответы приходят не в тот луч | в AllowedIPs пира на сервере больше одного адреса — след 1.1.0 |
| Скорость около 210 вместо 359 Мбит/с | настройка роутера не применилась: `taskset`, `rps_cpus`, `netdev_budget` из шага 8 |
| Скорость как у одного луча | все секции Forkop сидят на одном интерфейсе: `wg show owg2 transfer` не растёт |
| `obfmesh-balance on` не включает пакет | перевод секций не доведён: одна из них сидит на `bind_interface` интерфейса базового луча. Отказ штатный — довести перевод, шаг 10 |
| Один сервис подвисает и переоткрывается при работающей балансировке | та же причина, но пакет уже включён (`obfmesh-balance` до 1.1.0, где включение ещё не проверялось): соединения секции, ушедшие на чужой луч, гибнут в страховке. В `/proc/net/nf_conntrack` у них `packets=0` в обе стороны |
| Один поток не выше ~180 Мбит/с | это потолок одной сессии, не поломка |
| Сервис на роутере «останавливается» и встаёт обратно | `ls /var/run/obfmesh/admin-down`; watcher уважает этот маркер |
| После обновления пропал токен | конфиг перезаписан мимо пакетного менеджера; `/etc/config/obfmesh` обязан быть в `conffiles` |

Ключи, токены и `obfuscation_key` в логи и в вывод команд не попадают: в отчётах на их месте
`<есть>`. Если секрет всё же виден в выводе — это ошибка, а не особенность.
